### 新复现：正式过滤 flush 将未确认尾帧计为可靠停步

生产路径：`OvergroundSession.start_prepared` → `on_frame` → `GroundStabilityFilter.feed` → `halt` → `flush` → processor → `build_report`。不是 observation 旁路。

独立输入：2 段，样本 0..2099，只有样本 `[100,2095)` 的第 10..25 束遮挡，即原始接触 **1995 ms**；`[2095,2100)` 是清晰空场，随即手动结束。配置均为默认停步阈值 2 s、Software command。

实际输出，两模式一致：

```text
before halt: stops=[], processor.last_sample=2089
after halt: stops=[{'start_s': 0.0, 'end_s': 2.0}], processor.last_sample=2099
```

因此 halt 刷新队列后，原本未达阈值的原始接触变成了一个报告停步。`GroundStabilityFilter.flush()` 输出旧稳定 bits，未携带“这 5 帧已有原始释放候选、尚未获右侧确认”的可用性信息；processor 在 observation=None 路径把每个稳定遮挡帧更新为 last_reliable_sample。局部模型停步修复不能解决这个正式输入证据丢失问题。

按“停步必须有连续可靠观测”的规则，这是待修复的尾段证据缺陷；不主张将 10 ms 去抖整体撤销，也不能直接把未确认离地当作已确认离地。应区分稳定显示/去抖后的状态与可作为可靠观测的区间，保留原始尾部候选信息，避免幻增停步和时长。修复可能涉及 filter 输出契约及会话/处理器边界，尚未认领生产写入，请勿仅在 processor 中为本例写特判。

复现核心脚本（本轮经 stdin 执行，未新增或修改测试文件）：

```python
from qtpy.QtCore import QCoreApplication
from tests.test_ground_stability_filter import frame
from hardware.walking_preflight import PreparedDevice
from engine.overground_session import OvergroundSession
from config.walking_config import WalkingConfig
from config.overground_running_config import OvergroundRunningConfig
from engine.modes.walking_processor import WalkingProcessor
from engine.modes.overground_running_processor import OvergroundRunningProcessor
app = QCoreApplication.instance() or QCoreApplication([])
for cfg, factory in [(WalkingConfig, WalkingProcessor),
                     (OvergroundRunningConfig, OvergroundRunningProcessor)]:
    session = OvergroundSession(cfg(stop_type='Software command'), factory)
    session.start_prepared(PreparedDevice(frame(0).layout, 'stable', -1, 0, 3000))
    for n in range(2100):
        session.on_frame(frame(n, [(10,25)] if 100 <= n < 2095 else []))
    print(factory.name, 'before', session.processor.summary()['stops'])
    session.halt()
    report = session.build_report('manual')
    summary = getattr(report, 'walking_summary', getattr(report, 'running_summary', None))
    print(factory.name, 'after', summary['stops'])
```

### 当前代码逐层核验

1. `hardware/usb_worker.py::_on_frame` 在协议分包拼成完整 SensorFrame 时记录 `perf_counter_ns()`；`_publish_frame` 对每个完整帧直接发出 `sensor_frame_received`，没有“空场不发帧”或“相同位图不发帧”的过滤。1000 Hz 是设备采样时钟；主机到达时钟单独用于看门狗。
2. `SessionController.prepare` 在真实 UsbWorker 路径用 DirectConnection 将原始帧送到 `_GroundFrameInbox.on_frame`。该回调在锁内写入队列并更新 `quality.latest_received_frame`；算法和界面处理进度不决定该值。`drain` 限时批处理并在积压时用零间隔追赶，保持采样序号与到达时间不变。
3. `DeviceQualitySession.poll` 在 arm 后检查最新到达完整帧是否已过 1 秒，`freeze_input` 在同一 inbox 锁内二次核查，避免检查与停止之间的新到达竞争。当前主路径不是用 last_processed 时间判断；此前仅依赖 `last_frame` 的旧谓词可以复现假超时。
4. `GaitEngine.begin_quality_session` 调用 `OvergroundSession.start_prepared`，没有启动该 session 的旧 poll 定时器。实际主路径只有 quality gate 的看门狗。`OvergroundSession.poll` 本身仍是最后已处理帧谓词，直接调用或备用单独会话时不可据此推断具备 inbox 到达保护；本轮没有启用或修改它。
5. `SessionController.start` 对地面模式只发 arm 请求后返回，不重启/停止 USB；`prepare_walking_capture` 接管已有健康检查流或建立新流，取消健康检查计时器。`DeviceQualitySession.on_frame` 在 arm 后即使空场也发出 `frame_ready`，`GaitEngine.process_quality_frame` 的地面分支不受 `_paused` 拦截。没有查到点击开始后仅等人体触发才送帧的路径。
6. 更低层 `hardware/receive.py::start_auto_read` 仍在 Python reader 线程循环读取、解析并调用帧回调；有无字节、解析是否成功、是否能够拼成全部分段、回调是否异常，必须分别取证。它会吞掉读取/解析回调异常，因此报告仅有 data_timeout 不足以区分 USB 没字节、分包不完整与读取回调异常。当前看门狗监测的是完整 SensorFrame 到达，不是 USB 字节到达；有字节但持续不能得到完整帧仍应中止，不能用字节活跃替代可靠采样。

### 独立验证及修改范围

先原样执行 `tests/test_ground_session_replay.py`、`tests/test_main_acquisition.py`、`tests/test_sync_regressions.py`，**44 passed in 4.16s**。当前路径对 1.2 秒处理积压保持测量结果及原始导出一致；旧看门狗谓词回放为 data_timeout；真实 source_silence 仍中止。回放调用实际 gate/inbox/engine，但这是虚拟时钟逻辑验证，不是 Windows 定时器或 DLL 调度实测。已有 main acquisition 测试从 UsbWorker 分包回调独立核验完整空场帧未被节流丢弃，原始帧与设备采样时钟保留。

新增我方独立文件 `tests/test_ground_entry_timeout.py`，8 项覆盖走路/跑步 × 等待进入/刚建立首接触 × 队列积压/真实停流，均为 8 段、固定 1 束不可用。显式验证处理时间已落后 1.2 秒、1200 帧队列未消费时，新到达仍阻止超时；真正再无完整帧超过 1 秒时，包括未入场状态，均须 data_timeout。停止边界前接受的尾帧仍全部导出，不用于超时后的测量。结合上述三份原测试运行，**52 passed in 4.57s**。

初次新增测试的首接触前缀写为 40 帧，走路因默认最短接触 60 ms 尚未确认为入场而有 2 项失败；这是夹具条件不足，没有发生超时。校正为 80 帧（包含滤波延迟）后 8 项通过，没有借此修改算法或阈值。

本轮仅新增专用超时测试及本文档，**没有生产代码修复**：当前主路径未复现“持续有新完整帧到达却超时”，不应重复实现已存在的到达保护。若现场程序缺少该保护，最小行为修复边界是 `DeviceQualitySession` 与 `_GroundFrameInbox`，不涉及 processor；若出现字节活跃但无完整帧，边界在 `receive`/`UsbWorker`/assembler；若要补足诊断证据，先定义采集计数、最后字节/完整帧到达、停止时队列深度及异常记录的契约，再限定写入对应模块。不得只加大阈值，也不得等人体入场后才开始检测无数据。

### 仍需现场证据

需要 Windows 实际运行版本/构建来源、点击开始前后完整帧时间与序号、最后字节到达与协议异常、停止时 inbox 深度及最后已处理样本；若有原始回放，核对停止边界的已接收数量与导出数量。只有截图的 0 步、无回放不能证明设备没发帧，也不能证明当前队列修复已部署。当前新增测试仍不能排除 DLL 阻塞、Python reader 停顿、供电/USB 丢包、持续分包不完整及旧版本部署；这些是需要区分的候选原因，不是已诊断设备故障。
