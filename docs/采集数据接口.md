# 可变段数采集接口

此接口属于硬件采集层，与运动模式无关，设备长度不决定业务模式。五种正式硬件模式均经过完整 `SensorFrame` 与共享质量门；纵跳和跑步机仍限定单段，不能据接口支持多段推断这些模式已支持多段。

## 接入方式

```python
from hardware import UsbWorker

worker = UsbWorker(
    timeout_ms=10,
    chunk_size=2048,
    capture_command_required=True,  # 0918 固件：原生启停，并等待启动应答
)
worker.layout_detected.connect(on_layout_detected)
worker.sensor_frame_received.connect(on_sensor_frame)
worker.acquisition_issue.connect(on_acquisition_issue)
```

`on_sensor_frame(frame)` 获得完整设备数据，不接收八个位置参数。未配置段数时，`layout_detected` 在首张完整帧之前发出，`worker.layout` 随之确定。消费者必须处理 `acquisition_issue`，不能将设备无数据解释为人体离地。接收回调在 USB 读取线程执行；高频消费者应快速完成或使用有界队列，并显式报告自己的队列溢出。UI 应采用独立低频快照。

未传 `layout` 且未设置 `DAYU_SEGMENT_COUNT` 时，段数从第一个完整有效的数据帧自动识别：单包按 LED 数据字节数除以 12，分包按 `packNum`。支持 1..255 段；分包必须集齐后才确认布局。确认后本次采集固定段数，混入不同段数的数据报告 `layout_mismatch`，不会重解释已有帧。重新开始采集可识别新的段数。

这里识别的是**协议数据槽位数**，不是独立验证过的通电/在线段数。2026-09-27 末两段断电实测仍上报 96 字节 LED 数据，不能仅用载荷长度声明现场有八段在线。用户随后明确要求直接剔除全零段：主程序在准备阶段通过 `ActiveSegments` 自动选择有效段，不要求额外人工确认剔除，但界面和报告必须保留该决定的依据。

有效段选择与协议解析分开：一个完整自检观察窗（默认 3,000 个连续有效样本）内始终为 12 字节全零的段被剔除，对应接触语义的 96 束全遮挡；短时全零不剔除，缺帧、CRC 异常、无效数据和布局/流变化重置判断。剔除后对剩余段重新执行空场自检，因此默认需约 3 秒识别加 3 秒自检（设备采样时间）。准备中任一被剔除段重新出现非零数据则立即恢复并重做自检。全部全零显示“无可用段”，不能构造零段 `DeviceLayout` 或通过开始门。

本次开始后有效段映射冻结；运动中不删段、不恢复段，也不因全零自动结束测试。恢复信号进入质量事件，下一次准备时重识别。有效布局保留原段标识、方向和物理坐标，中间剔除不能压缩空隙；跨剔除空隙的运动中断事件配对。原始 `SensorFrame`、全协议槽位数据与设备时钟不改写，只有算法输入和有效跑道显示投影到所选段。`beam_quality.preflight.segment_selection` 保存原始布局、原/有效段数映射、剔除索引和观察样本数，索引从零开始；报告、历史和 Excel 沿用该快照。全零可能由断电或遮挡等造成，记录称“自动剔除全零段”，不声称已诊断掉线。

`DAYU_SEGMENT_COUNT` 或显式 `layout` 可用于固定预期段数并校验硬件。仅设置 `DAYU_SEGMENT_ORDER` 时，段数取其项数。顺序的第 i 项表示线上第 i 组对应的物理段编号（1..N），例如三段线序 `2,3,1`。显式布局优先于环境变量。物理线序、光束间距、段间缝隙与安装方向不能从协议自动判定；自动识别时采用恒等线序和名义 1m 几何，需要按现场标定覆盖。

主程序采用 2048 字节读取块，USB 默认超时经空场单变量验证选择 10ms（参考包的 1ms 不直接照搬），可通过 `DAYU_TIMEOUT`、`DAYU_CHUNK` 覆盖。采集启停只调用 DLL 的 `StartCapture` / `StopCapture`，Python 不再额外拼接控制命令。`capture_command_required` 保留原名称及环境变量兼容，默认 `True`，表示启用启动排空和应答确认；不返回应答的旧固件可设置 `DAYU_CAPTURE_COMMAND=0` 或显式传 `False`，仍调用 DLL 原生启停。段数仍由完整数据自动识别，与握手配置和运动模式无关。

启动边界以本次 FPGA 采集应答为准：先调用 DLL 原生 `StopCapture`，同步读走旧数据与旧应答，直到连续 20ms 无输入（最多等待 1 秒）；再启动读取线程、开放本轮应答接收，调用 DLL 原生 `StartCapture` 并等待 `ACK=0`（最多 1 秒）。不能先启动 DLL 再等输入变空，因为 `StartCapture` 本身已使能 FPGA。开始等待本轮应答之前收到的 ACK 不计入握手，应答前的 DATA 不进入组帧器、布局识别或质量判断。原生启停失败、排空超时、启动应答超时/拒绝都明确报启动失败并关闭数据入口，迟到应答不能复活失败的采集；必须显式重试。旧固件免应答配置跳过排空与握手。运行中 ACK 不重置帧号检查，真实倒序仍报错。

## DeviceLayout

`segments` 按物理位置递增排列。每段对应当前硬件的 96 个光束、12 字节，包含：

| 字段 | 定义 |
| --- | --- |
| `segment_id` | 稳定段标识 |
| `wire_index` | 在线上 payload 中的组索引，0 起 |
| `origin_m` | 该段物理位置最小的光束中心，米 |
| `pitch_m` | 段内光束中心间距，米 |
| `reversed` | 线上位序与物理位置顺序相反时设为 True |

`DeviceLayout.linear(N)` 采用每段起点相差 1m、段内间距 0.0104m 的名义几何值。精确位置应通过 `SensorSegment` 显式配置；不能把名义值当成安装标定结果。`positions_m` 与输出位图一一对应，段间接缝保留实际距离。

`invalid_bit_indices` 是已知失效光束的全局物理索引，0 起。它只影响 `valid_bits`，不改写原始遮挡数据。布局本身不可变，帧共享同一布局对象；录制时每个流保存一次完整布局即可。

## SensorFrame

| 字段 | 定义 |
| --- | --- |
| `stream_id` | 本次采集流 ID，显式重启采集后改变 |
| `layout` | 设备布局，不包含走路、跑步或跑步机配置 |
| `frame_index` | 设备 uint32 帧号 |
| `sample_index` | 自本流第一张完整有效帧起的采样序号，保留跳号间隔 |
| `sample_rate_hz` | 1000Hz |
| `sample_time_ns` / `sample_time_s` | 从采样序号得到的相对采样时间 |
| `time_source` | `device_frame_counter`，不是主机到达时间 |
| `received_monotonic_ns` | 组帧完成时的主机单调时钟，仅用于接收延迟/顺序诊断 |
| `wire_payload` | 完整原始线序 LED 字节，1=光路未遮挡，LSB 优先 |
| `contact_bits` | 物理顺序的紧凑 bytes，每个元素为 0/1；1=光路被遮挡 |
| `valid_bits` | 同长 bytes，1=该光束可用；0 不是未遮挡 |
| `dropped_frames_before` | 与前一输出帧之间缺失的采样数 |
| `quality_flags` | 例如 `frame_gap`、`all_beams_blocked` |

光学遮挡不等同于已判定的人体触地；这由后续业务算法解释。全亮和全灭的完整有效协议帧均保留，全灭增加 `all_beams_blocked` 标记。新通道不采用整帧稳定确认，也不删除短时遮挡。

采样时间按 `sample_index / 1000` 计算。同一次 USB 读取内收到多个帧，仍按设备帧号保持各自的 1ms 间隔。uint32 正常回绕可连续展开。帧号倒退可能是迟到数据或设备复位：报告 `out_of_order_or_reset` 并拒绝该帧，不自动猜测新的时间原点；确认设备复位后重启采集。不能跨 `stream_id` 直接相减时间。

当前固件没有分段采样时间字段，完整组帧按同一 `frame_index` 组织；接口不宣称已经独立验证各段内部同步，也不自动补偿未知段间延迟。

## 分包、错误与兼容

- USB 外层帧头、CRC8、长度和帧尾不变；长度字段为小端。
- 默认帧号为小端，与 0918 原始日志一致。已确认使用大端计数器的旧固件可在连接前设置 `DAYU_FRAME_INDEX_BYTEORDER=big`；底层解析器也支持显式参数。
- 支持一个完整 payload，或者 N 个各含 12 字节的段分包；分包编号兼容从 0 或 1 开始，同一流中保持一致。
- 布局声明 N 段时，完整 payload 必须恰好是 `12*N` 字节。软件支持 1..255 段，这是当前分包计数字段的上限，不是实际硬件级联能力承诺。
- 不同帧号不能拼接。缺包不会补零，也不会借用上一帧；超时 1s 后报告 `incomplete_frame`。未完成组帧缓存最多 128 项，超限报告 `assembly_overflow`。
- 冲突分包、编号基准变化、长度错误通过 `acquisition_issue` 报告。CRC/帧尾错误由协议解析器丢弃并逐字节恢复同步；若因此缺失采样，后续完整帧的跳号会反映出来。
- 完整帧按完成顺序输出；晚于更新帧才完成的旧帧报告异常并丢弃，绝不逆序传给消费者。
- `raw_contact_signal(list, float)` 仅对单段保留，时间仍为历史 `perf_counter()` 基准。它不携带新质量信息；新消费者应使用 `sensor_frame_received`。多段不会偷偷截成单段喂给旧算法。
- `led_bits_signal` / `led_contact_signal` 是完整设备、可节流的显示通道。地面模式已通过完整布局接入足迹视图、回放和全宽导出；旧 `led_con` 等固定 96 位组件不作为多段接口验证依据。

主项目统一使用 `hardware` 下的新接口。`led_con_package_8m_0918` 保留为现场参考采集包，本次不复制一套接口进去，也不改变它原有的八面板显示及过滤行为。接入主项目时使用上面的统一 Worker。

参考程序用于显示的“重复至少 3 帧且持续至少 10ms”整帧过滤不进入运动算法或自检原始输入。主程序只在自检诊断层按束分别做稳定确认：至少 3 帧且 `sample_index` 跨度 ≥10（1000Hz 下 10ms），丢帧重置。短脉冲保留审计；待确认变化暂时取消开始资格；当前观察窗内大范围变化独立出现 ≥3 次，提示采集不稳定并禁止开始，详见[质量约定](mode-routing-and-beam-quality.md)。运行中质量观察仍消费未经过该确认的数据。

主程序每帧继续检查质量与开始资格；约 10Hz 生成界面诊断快照，就绪/失效或故障清单变化立即发布。不可变布局缓存光束坐标，避免每帧重建全程几何。性能优化不补帧、不修改设备计数，也不以保留上一张画面掩盖采集异常。

### 已跨过缺包帧的分包清理

接受更新的完整帧并通过设备序号标记丢帧后，立即清除已经落后的残留分包，避免一秒后再把同一次缺包当作当前异常。比较按 uint32 回绕规则执行，尚在未来的分包继续保留并正常超时。迟到或计数回退的包仍报告 `out_of_order_or_reset`；重复帧仍进行完整载荷冲突检查。
