## 接口处理

- 优先调用 `piccrequest_ul`，保留其全部 7 字节输出，按厂商示例仅将状态 0 视为有效。
- DLL 没有该入口时使用 `piccrequest` 的 4 字节输出；说明书明确状态 0、10 下序列号有效。
- `piccrequest_ul` 返回 9 时，尝试 `piccrequest`；只有后者返回 0 或 10 才采用其序列号，否则保留原错误。本次实物 F08 卡出现 7 字节接口返回 9、4 字节接口成功的情况。
- UID 使用大写十六进制，保留前导零和末尾零；不能仅凭末尾 `000000` 判断卡号长度。
- `pcdbeep` 的参数是 32 位无符号整数，单位为 2 毫秒；Python 方法接收毫秒并转换。
- 硬件模式失败会显示错误；模拟模式必须显式传入 `--simulate`。
- 运动员页面、验证窗口和命令行会区分无卡、驱动异常、超时等状态。

此前试验代码曾裁掉末尾三个零字节。如已用该代码绑定卡片，升级后应核对并重新绑定受影响的卡片；不会自动猜测或改写已有绑定。
4 字节卡通过 7 字节接口返回的具体形式，应使用实卡与厂商同接口示例核对。

## Mac 上的验证

不连接设备也能验证模拟流程。从项目根目录运行：

```bash
python -m hardware.rc200u --simulate --once AABBCCDD
python -m tools.rc200u_probe --simulate
```

连接设备后，可通过以下只读命令检查 USB 枚举：

```bash
system_profiler SPUSBDataType
ioreg -p IOUSB -l -w 0
```

检查厂商 ID、产品 ID、产品名称、接口类以及插拔前后的变化。
资料中的 CH375 INF 包含 `4348:5537`、`1A86:5537` 等 ID；这是驱动匹配列表，不能据此认定实物一定使用其中某个 ID。
Mac 能识别 USB 设备不代表 Windows DLL 已可调用，也不代表已成功读取 UID。

## Windows 实机步骤

1. 连接读写器，按资料包安装匹配的驱动，在设备管理器记录硬件 ID 与驱动状态。
2. 单独运行厂商测试工具，确认读取设备编号和卡号。完成后退出工具，再启动本项目，避免同时访问设备。
3. 确认 Python 与 DLL 位数一致。当前 `hardware/OUR_MIFARE.dll` 与资料包的 x64 版本 SHA-256 一致，适用于 64 位 Python。
4. 在已安装项目依赖的环境中，从项目根目录运行：

```powershell
python -c "import struct; print(struct.calcsize('P') * 8)"
python -m hardware.rc200u --once
python -m hardware.rc200u
```

未贴卡时预期 `status=8`，贴卡时应出现 `uid=... status=0`。
`backend=hardware` 只表示使用 DLL，需以设备编号和实际 UID 作为通信成功的证据。

如使用其他 DLL，可显式指定：

```powershell
python -m hardware.rc200u --dll "C:\path\to\OUR_MIFARE.dll" --once
python -m tools.rc200u_probe --dll "C:\path\to\OUR_MIFARE.dll"
```

主程序可通过环境变量 `IRON_JUMP_RC200U_DLL` 指向匹配的 DLL。

5. 运行 `python -m tools.rc200u_probe`，选择已有运动员并绑定；验证移开后再次贴卡、连续贴卡、另一张卡、解绑和重复绑定限制。
6. 退出验证工具，启动主程序，在运动员页面重复上述操作，确认刷卡选中正确档案。
7. 测试运行中拔插读写器，记录异常状态与重新连接后的恢复情况。若厂商 DLL 未自行恢复，重启程序并记录现象。
8. 对照厂商工具记录同一张卡的 UID、字节顺序和长度；发生差异时核对两边使用的寻卡接口，不能直接裁剪或倒序卡号来匹配。

错误参考：8 无卡；9 多卡或防冲突失败；22 DLL 或驱动异常；23 驱动或连接异常；24 超时；25–28 USB 传输或校验异常。
