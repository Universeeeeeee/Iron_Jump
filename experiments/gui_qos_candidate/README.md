# 原 GUI QoS 症状协议准备：尚未启动

`06444b6` 的固定计算试验有 18.11% 消费改善，但联合原生吞吐门槛失败；`3cb9401` 又确认 SSH 与交互计划任务的启动会话和优先级不同。因此这里准备一个**独立 GUI 症状可行性协议**，不把此前机制门槛改成通过，也不声称已经修复积压。

## 已落实

- 使用既有保存 Walk 输入、原 GUI/真实模型/实时 latest-only 行为，以及两组共同模拟原生 SDK。原始输入、正式源文件、外部库及既有 finalization 链哈希继承旧 GUI 基准；新的依赖另行绑定。
- 唯一变量是实验目标进程执行速度 QoS：default 不调用 setter，optout 接管 execution-speed 位并关闭该位节流。没有相等性检查候选、原生预热探针、绘图修改或 OpenCV 设置。
- 两组都要求交互会话、Windows Qt 后端及实际 BelowNormal（16384）优先级，保持已验证的旧计划任务环境。不是把生产桌面入口认定为 BelowNormal。context gate 拒绝 Session 0、错误优先级、意外初始策略及跨会话比较，不自动“修正”。
- 目标入口复用只读 context 查询、原 QoS 适配器和既有 GUI finalization；模拟 SDK 与原处理方法保持。入口结束保留实际 QoS 和原方法/模块未变核验。
- 本地与 Windows 各 12 项测试通过：启动条件、无严重基线、输入迟到、失败窗口、残留延迟/队列、不完整配对等失败路径均拒绝。

## 预先规定的症状判据

固定 4 对，顺序 default/optout、optout/default、optout/default、default/optout。全部窗口保留，不因基线不复现而追加。仅当全部语义、来源、运行环境、最终清理验证合格，才评价：

1. 至少 3 个默认窗口同时达到 observed deque ≥1000 与 contact→paint 最大值 ≥1000ms。
2. 每对的**计划输入接触时刻至首次绘制**最大延迟改善，几何平均下降至少 20%。同时保留实际接收时刻延迟，防止输入变慢虚假改善。
3. 每个候选窗口计划输入至绘制最大延迟 ≤250ms，连续队列峰值上界 ≤250。
4. 每个窗口正式段最大输入迟到 ≤150ms。

这些是本协议新增、事前冻结的可行性判据，不是旧现场 SLA，也不替代 3%/1% 扰动资格。若不满足，停止该协议，不调阈值或替换失败窗口。动态视频/推理/绘制量保留为结果，不能事后配平。即使通过，也只支持相同模拟 SDK GUI 协议中的改善，真实单 USB 现场仍需验证。
