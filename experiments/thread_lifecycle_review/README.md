# 历史线程生命周期事件的独立复核

本轮只重新解码历史合成 ETL，未启动 WPR、采样器、模型、GUI 或现场采集。源为既有 `cpu_pair1_cpu/trace.etl`，SHA256 与历史清单一致：`274aea8c38703565f35587fec4d3b02e40c1a523c6b2a28a89e1c431c7ba7184`。

## 已获得的证据

原 `ReadStacks.cs` 对 Thread opcode 1–4 按载荷 PID 保留事件，不受指定角色 TID 列表限制，因此具备保留目标进程其他线程生命周期的基础能力。

Windows 自带 tracerpt 对同一 ETL 做独立解码。目标 PID18280 的 **16 条事件、8 个 TID** 在现有读取器与 tracerpt 原始载荷中，其 opcode/version/PID/TID/全部载荷字节完全一致。不是只比较前八字节或计数。

历史 fixture 的 cpu_a、cpu_b、qt_wait、system_wait 四个控制线程均具有实际 Start/End 事件，其 QPC 区间包含对应 GetThreadTimes/cycles 计数窗口。前后线程创建时间一致。原读取器的 header/consumer/buffers lost 全为 0，tracerpt 汇总也报告事件丢失为 0。

这验证了既有线程事件保存及已知角色时间包围关系，不等于全部生命周期场景已经校准。剩余四个 TID 没有独立 fixture 角色记录，不赋予角色。没有把零丢失报告提升为任意协议的绝对完整性证明。

## 保留的失败与限制

1. 第一版 XML 提取按 Provider Guid 查找得到 0 条。检查实际 XML 后发现 tracerpt 使用公共内核 Provider Guid，将经典线程 GUID 放在 ExtendedTracingInfo/EventGuid。原错误输出保留，不能解释为没有线程事件。
2. 改用 EventGuid 后能识别线程事件，但命名属性仍为空：tracerpt 对线程载荷报告 **15005（模式不匹配）**。全系统生命周期事件中共记录 6386 次此类模式错误。该失败与事件丢失不是同一回事。
3. 第三版仅从 ProcessingErrorData 保存原始 EventPayload，保留错误码，与项目原始字节交叉比对。它没有恢复命名字段，**没有验证 Win32StartAddr 或其他起始地址偏移**；不以猜测的地址做模块归属。
4. DCStart/DCEnd 是采集时的存量线程记录，不是实际创建/退出。新纯逻辑检查保留左右截断，拒绝重复开始、无起点退出，分开 TID 再利用的多个生命周期。
5. 历史 ETL 不能追溯最近固定模型诊断新增的 TID8700/11912/23256。那一窗口没有 ETW，原线程集合失败与约2047ms未解释余额保持。
6. 原栈闭合门槛、观察扰动和3%/1%失败仍然有效，不能借生命周期字段核对变成通过。

## 验证与下一步

六项生命周期逻辑测试通过，原归档/ETL/事件哈希复核通过，四个已知角色的计数时间窗交叉检查通过。149.7MB XML 保留在 Windows 独立复核目录；仓库只保存派生选中载荷、哈希、失败输出、脚本和报告，不复制完整 ETL/XML。

下一步应先补线程创建—退出均在枚举之间的专门合成控制，并校验采集全程的事件丢失、PID/TID/创建时间与时钟。起始地址另需与当前版本模式或独立系统接口核对；在此之前只报告已验证的生命周期，不解释未验证字段。无需设备或真人测试。
