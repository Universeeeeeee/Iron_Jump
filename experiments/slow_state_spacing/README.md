# 跨进程间隔条件控制：冻结六窗、两次五分钟间隔

依据758ad4c的27窗时间线，验证一个明确候选条件：在每次都启动新进程、原始工作不变时，五分钟无本实验目标间隔是否能重复使快态恢复为慢态。它不测试优化收益，不扩展进程隔离，不改变正式程序。

固定六窗：initial（初始状态不受控）、short01（前窗退出后5s）、long01（300s）、short02（5s）、short03（5s）、long02（300s）。每窗均为原始串行固定工作：模型先ready，原42,237帧准备，6,824帧消费，然后220次真实模型调用；原图像、逻辑时间、完整模型返回及报告/quality/timeline/raw必须等于旧独立基准。模型线程存在但实际推理区间不与消费者重叠。串行是此固定协议的共同条件，不改正式视觉并发策略，也不与GUI协议跨窗相减。

复制cpu_state_observation/workload，唯一增加原model.open前后两个墙钟标记。原准备CPU、线程CPU、全进程CPU/cycles和七个进度点保持。没有主动原生计算探针、额外模型调用、预热、GUI、SDK、真实相机/光栅、人体、USB或Run，不改OpenCV8、GC、电源、优先级或亲和性。

所有窗皆新进程，因此进程重启因素保持；干预仅为上一进程实际退出观测至下一次Popen之前的间隔。允许启动迟到<=2s，实际间隔保留；报告验证等工作也在间隔时钟内，不能把它剔除。脚本不为凑状态加轮、不替换失败。任何身份/原报告/CPU账本/退出/间隔失败停止后续窗，超时保留PID/锁，不自动杀进程或重启。

长间隔中控制器每5s读取GetSystemTimes和GetSystemPowerStatus，不执行目标负载。Windows kernel时间包含idle，按总kernel+user减idle核对忙碌率；不以标称CPU频率或策略getter解释速度。长间隔资格要求至少50个连续区间、相邻采样<=6s、每次读取<=50ms、系统忙碌率中位<=15%且最大<=50%、AC=1。这里只是系统总量的低负载条件，不能保证每核空闲、没有后台活动或温度不变；读取本身也未获3%/1%扰动资格。所有失败读数/资格不满足保留，不通过追加空闲补足。

状态标签沿用既有固定工作分界：准备墙钟>=4300ms且220次模型调用中位>=30ms为slow；准备<=3500ms且模型中位<=26ms为fast；其他均intermediate。CPU计数不换算GHz，wall-CPU不当GIL等待。

只有short01、short03分别为fast，且两个后继long01/long02都变slow、两次长间隔低负载/AC/时长资格均通过，同时long01后short02/03为fast，才支持此五分钟条件在本夹具内重复触发慢态。否则结论为未确认该条件，不能据此否定更长间隔、缓存、频率或其他状态。六窗是探索性机制控制，不是临床或GUI实时性验收，不能从顺序推导硬件原因。

所有源码/依赖/原始数据/模型、状态判据与预算在执行前冻结于plan01；3项规则测试涵盖CPU计数语义、联合状态和启动迟到。旧CPU/CSwitch、3%/1%失败、故障锁与历史窗口不变。完整数据归档留忽略runs/Windows，派生结论及代码推送现有分支。分析结果另附，未完成前不宣称条件成立。

这次直接证实：在此固定原始串行工作条件下，连续完整运行六次并不必然恢复，慢态能持续跨越两次实测低负载间隔。它比“总是第一次慢、第二次快”更精确，不能把旧GUI自然恢复归给运行次数本身。

同时，model.open首窗5.236秒、后五窗2.362～2.418秒，持续执行的准备/消费/推理却未变为快态。因此可把**初始化一次性附加耗时**与**持续执行慢态**作为不同观察对象；这不是已确认文件缓存、睿频或具体模型核原因。没有给CPU/GIL份额或真实GHz命名。
