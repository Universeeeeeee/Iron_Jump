# 模型就绪与共同视频帧复核

## 结论

不能将上一阶段发现简化成“等待模型 ready 即可修复”。首窗确实在 armed 后 952.6 ms 才就绪，但距离第一有效接触仍有 3.605 秒；第二个慢窗在 armed 前 2.539 秒就绪，距首次接触有 7.093 秒。后六窗相应提前约 7.95–7.98 秒。所有八窗在第一次接触前均已完成 adapter.open。

源码关系：`vision/service.py` 在 `adapter.open()` 返回后发出 ready；实验 `gil_gui_calibration/replay02.py` 的启动条件只有光栅质量 ready、SDK start 成功和已消费检查样本，不包括模型 ready。这里分别核对了真实 model_open 区间和 service_status 事件，并非仅信任一个布尔 getter。ready 不证明预热完成或性能稳定。

## 共同帧描述

按 `(frame_index, sample_time_s)` 标识，八窗共有 235 帧。各窗内部标识唯一，原始全部 373–375 个模型调用仍保留，未用共同子集替换 A/B 主终点。

| 窗口 | 共同帧调用墙钟中位数 ms |
|---|---:|
| pair01 原版 | 35.464 |
| pair01 候选 | 32.944 |
| pair02 原版 | 20.322 |
| pair02 候选 | 19.911 |
| pair03 候选 | 19.749 |
| pair03 原版 | 20.135 |
| pair04 候选 | 19.950 |
| pair04 原版 | 20.168 |

235 帧中每帧的首两窗中位数都高于后六窗中位数，逐帧比值中位数 1.670。这是结果后按时间顺序分层的描述，不能当作 235 个独立样本计算显著性或干预收益。共同标识不等于重新验证像素一致，尤其不能保证状态化模型的先前帧历史相同。

该结果削弱“仅因本轮挑中不同视频帧而变慢”的简单解释，仍不能区分模型计算、调度、GIL/其他同步、机器状态和模型内部历史。

## 证据边界与下一步

现有固定任务 CPU/cycles 数据来自另一协议：完整固定任务组、无 GUI/SDK，不能填到这八个 GUI 窗口。该协议的 CPU 同时区间 −3.783%..+7.733%，24 对规划精度约 1.227%，未达到 1%；其失败不因本复核改变。PMU 可枚举也不代表已获得有效硬件计数。

下一项有判别力的准备工作是对“模型墙钟变慢”同时观测 CPU 交付与等待，而不是只加一个 ready 门槛：先用独立合成执行/睡眠/竞争控制验证计数边界、身份和读数误差；随后才设计保留原始启动窗口的固定实际负载校准。不要从不同轮次拼装不存在的 CPU/GIL 分解，不立即重复 A/B，不更改正式线程或模型策略。

本轮完全离线。归档逐文件哈希复核；模型 ready 与 open 的顺序、就绪早于首次接触、每帧标识唯一均通过。重复标识拒绝与时间戳参与身份的两个测试通过。根因和正式修复未完成。
