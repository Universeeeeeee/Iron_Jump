# 会话输出桥接：有界队列与原生通道故障合成验证通过

`a5c133f` 已验证原会话命令和通知的基本交付，但actor仍直接写Pipe，慢父端可能阻塞child主事件线程。本阶段只补这个会话隔离候选的输出组件，不增加性能采集工具，不修改旧actor或正式程序。

## 边界与失败语义

`Outbox` 在生产者侧序列化已有数据值并立即入队，单独writer执行Pipe写。默认接受队列最多128条、8MiB，**正在写、尚未返回的一条也计入条数与字节限额**。序号必须连续。入队后的值已脱离原可变对象，队列不latest-only化、不静默删事件。

超条数、超字节、单包过大、序号错误、序列化失败或发送错误都会锁定首次失败并停止接受。writer的停止超时也记为失败，之后即使写入返回、writer退出，`finish`也不能改为成功。writer不会在失败后继续发送排队数据。未确认包可独占写入保全目录并核对SHA；拒绝新包保留长度/序号/哈希，组件不无限保留被拒绝的包体。

这些界限只覆盖**已接受的序列化缓冲（含inflight）**，不包括调用方原对象、序列化临时内存、容器开销及OS管道缓冲，不能把8MiB宣称为总进程内存上限。`send_bytes`返回也不是父应用收到；组件永远不自行将`parent_application_receipt_confirmed`置true，端到端成功仍需接收端独立核对。

## 固定三个Windows原生Pipe场景

运行前冻结 `plan01.json`，本地和Windows各9项测试通过，随后只执行一次三场景队列，没有追加或替换。

| 场景 | 独立交付/故障证据 | 最终状态 |
|---|---|---|
| normal | 实际read端收到8个精确值，序号1–8；writer完成8次写，缓冲清空 | writer退出，本地transport_complete=true；接收端证据另记 |
| disconnected_peer | 实际关闭read端，writer收到Windows BrokenPipeError232；包1和错误详情保留 | transport_complete=false，writer退出、包1未确认 |
| native_backpressure | 原生Pipe已存在可读数据，writer的2MiB写调用仍未返回且接收端未读；接受inflight+queued共2条，再入队拒绝 | 首次失败message_limit；恢复读取后仍false，包2仍未确认 |

背压窗口测试限额为2条、6MiB，峰值2条/4,194,394字节，没有把inflight从限额中漏掉。停读阶段writer存活且写调用未返回，生产者已经到达上限并返回故障，证明它没有等待该原生写完成才报告超限。首次保全时包1/2均未确认；随后read端实际收到包1，writer退出，但故障状态保留，包2不再发送。

`review01.py` 独立核验归档、各场景结果及保全合成包的实际值与哈希。未确认快照只描述保存时刻，写可能后来返回；不能据快照断言包从未到达父端。故障场景contract_pass=true是预先定义的**正确拒绝/保全行为**，不表示传输成功，也不覆盖其中transport_complete=false。

## 还没有验证什么

这只是同一合成进程中的独立原生端点/线程，**不是实际测量actor的父进程死亡试验**。没有证明传输失败后原reader/inbox/quality/engine能正确冻结、排空并保留完整局部档案/报告；也没有真实GUI输出背压、吞吐、延迟或3%/1%扰动资格结论。

下一步只将组件接入新的实验actor版本，保留当前所有旧版本：

1. producer或writer首次失败使会话进入明确故障态，Qt层不会忽略异常后继续宣布成功；由原控制器有序停止/冻结，保留全部已接受raw和实际入口尾部。
2. 传输失败时，即使父端收不到结果，也必须将原局部报告/质量状态写到child证据目录。失败不能成为跳过本地保存的条件。
3. 先保存未确认输出及writer状态，停止未确认时保留锁；没有父端接收证据不得宣布端到端交付完成。不能为清理而自动重启或删除失败窗口。
4. 另行冻结正常完整输入、父端断连、父端停读三个保存输入场景；验证真实actor停止和档案，之后才接GUI并发。

这是产品桥接的必要故障边界，不是新的通用观测框架；不同时试QoS、优先级或算法优化。
