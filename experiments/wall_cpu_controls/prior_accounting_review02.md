# 固定任务 CPU 精度失败的计数分解

## 新定位

复核 `fixed_work_variance` 原始四对 OFF/OFF，全归档哈希通过，未改变既有端点、配对或失败结论。每窗进程 CPU 为约 13.8–14.5 秒，远长于一次 20–35 ms 的模型调用。

| 对次 | 进程 CPU 差 ms | 用户态差 ms | 内核态差 ms | 两个命名线程合计差 ms | 进程 cycles 变化 |
|---|---:|---:|---:|---:|---:|
| 1 | −15.625 | +46.875 | −62.500 | −31.250 | +1.486% |
| 2 | +656.250 | +609.375 | +46.875 | 0 | +0.023% |
| 3 | +390.625 | +359.375 | +31.250 | +109.375 | +0.697% |
| 4 | −15.625 | −62.500 | +46.875 | 0 | +1.209% |

第二对是关键：消费者 CPU 减少 140.625 ms，模型入口线程 CPU 增加 140.625 ms，两者抵消；进程 CPU 却增加 656.25 ms，进程 cycles 基本相同。这将精度问题进一步定位到**尚未分配到这两个命名线程的进程计费部分及其测量**，而不是仅由消费者自身执行时间变化解释。

每窗“进程 CPU − 两个命名线程 CPU”约 8 秒。它包含原生线程池等其他线程，也可能包含计量窗口差、边界工作和多线程计费粒度误差；不能直接命名为模型内部 CPU 或线程池等待。尤其不能按进程只有一次 15.625 ms 量化误差来排除计费误差，因为原生线程数量、生命周期和各线程计费未完整保存。

相同完整任务与推理返回不代表内部指令量完全相同。cycles 也不是精确退休指令或物理频率，不能据此把 CPU 波动宣布为“只有测量错误”。这正是需要下一级线程证据交叉核验的地方。

## 并发时间线补充

八窗在消费者仍工作时，模型调用墙钟中位数 37.4–42.5 ms；消费者完成后为 32.1–32.8 ms。跨越完成边界的调用单独保留。此为时间顺序关联，包含帧顺序/模型历史/时间趋势，不能当作去掉消费者的因果 A/B。

固定任务与 GUI A/B 协议不同，以上计数不搬用到 GUI 慢窗，不能估算它们的 CPU/GIL 份额。

## 下一项计量必须满足的具体条件

1. 保留进程计数，并覆盖消费者、模型入口及原生池线程；按 PID/TID/创建时间持有句柄，不能只用两个 Python 线程代替进程。
2. 所有开始读数都在释放工作门之前，所有结束读数都在模型关闭及线程退出之前；保存每个读数的真实时钟括号，既验证单次读取，也验证整组遍历的宽度。
3. 进程与线程 CPU 和 cycles 分别核对；差值作为未解释余额保存，不强行分摊。前后枚举相同仍不能排除窗口内短命线程，必须明确标记这项证据缺口。
4. 先用已知固定数量工作线程验证汇总和生命周期，包括在枚举间退出的反例；随后才用于固定原处理链与真实模型。任何线程未知、句柄读失败或终止未确认均禁止宣告归属完整。
5. 加入计量前先冻结工作、窗宽、A/A 和扰动方案；旧 3%/1% 失败保持。不能用删除 CPU 端点、cycles 归一化或重复同批来获取通过。

本轮只离线复核，尚未部署新计量、运行新负载或修改正式程序。根因与正式修复仍未完成。
