# 墙钟、线程 CPU、进程 CPU 的独立合成控制

目标是为模型早期变慢的下一步观测验证计数边界。只运行一个冻结三窗合成 cohort，不加载项目、模型、Qt、NumPy、设备或 ETW，不调整优先级、亲和性、电源或采样间隔。失败即终止，不重复替换。

## 已验证

| 控制 | 墙钟约 ms | 本线程 CPU ms | 进程 CPU ms | 工作线程 CPU ms |
|---|---:|---:|---:|---:|
| 本线程计算 | 2000 | 1968.75 | 1968.75 | — |
| 本线程睡眠 | 2001 | 0 | 0 | — |
| 工作线程计算、本线程等待 | 2001 | 0 | 2000 | 2000 |

计算控制以实际算术块及结果 49995000 确认执行；睡眠/等待由独立已知控制路径产生。进程和线程创建时间、PID/TID、计数单调性、生命周期、读取括号和工作线程包含于主窗口均通过。独立复算与单线程 CPU 不超过墙钟的宽容边界检查通过。

计数通过 `PyDLL` 读取，短读数期间保留 GIL，避免工具本身引入一次 WinDLL 释放/重取 GIL。这只是边界设计，不证明低扰动；读取包括线程与进程计数以及 Python 包装成本。100 次边界读数宽度为 44.3–172.3 µs，均通过预定 1 ms 上限。它们未放进真实 GUI 负载，不能换算成真实应用开销比例。

六项边界测试覆盖身份变化、创建时间变化、计数回退、慢读取、重叠边界和合法区间；本地通过，Windows 启动链也在运行 cohort 前执行测试，非零退出即禁止进入 cohort。三个控制完成后查询无 Python/observer 进程。原 Windows 锁和结果保留，取回结果 SHA 与远端独立 Get-FileHash 一致。

## 明确限制

- `thread_time_ns` 与 `GetThreadTimes` 同属 OS CPU 计费，读数一致不是独立硬件真实性证明。
- 等待控制可有少量 cycles，CPU 为 0 也不是绝对未执行；边界读取和计费粒度仍存在。
- 记录中出现 15.625 ms 的 CPU 计费步进。20–35 ms 模型调用不适合直接按单调用做 CPU/等待占比，零值不能当作全程等待。
- 进程 CPU 包含其他线程，不能分配给单个模型调用或 GIL 持有者；本次工作线程控制直接展示了主线程 CPU=0 而进程 CPU=2000 ms。
- cycles 只作单调执行证据，不解释为退休指令、物理频率或 GIL 等待时间。
- 这是粗粒度控制，>=500 ms 执行、<=250 ms 空闲门槛只用于合成分类；未放宽实际负载的 3% 等效/1% 精度或原生栈门槛。

## 下一步

在固定时间窗口聚合模型线程、消费者线程和整个进程的计数；记录原始模型初始化及 ready 边界，保留全部慢/未就绪窗口。先完成新增边界计数在固定任务上的 OFF/OFF 方差和 OFF/ON 扰动检验，再用于动态 GUI 状态对照。不得将线程墙钟减 CPU 直接称为 GIL 等待，也不得用独立进程本轮通过替代 GUI/真实模型负载验收。

当前没有新增 GUI A/B 或现场测试，没有修改正式程序。模型/消费链变慢的具体来源仍待证明。
