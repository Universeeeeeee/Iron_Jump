# 固定原处理链与真实模型：线程集合实际发生变化

## 结果

第三次启动尝试 `diagnostic03` 完整完成，原始 6824 帧处理链、图像像素哈希、220 次模型返回摘要和完整报告均与既有固定基准精确一致。新增计量没有改变正式代码、NumPy、滤波、Processor 或线程结构。

## 含义

原入口在模型 `open()` 完成并 ready 后才放行工作；本次初始枚举也在 ready 后。因此“模型已打开”不保证整个进程线程集合已经稳定。需要考虑初始化后的新线程，不能预先只绑定模型入口线程或 ready 时已有的池线程，就声称覆盖后续所有计算。

这不证明新增线程属于模型库，也不证明全部 2046.875 ms 差额由它们产生。还可能有前后枚举之间已退出的短命线程、读取边界成本及 OS 计费量化。没有线程起始地址/生命周期事件，不作库级归属。

新窗口不能替代历史 OFF/OFF 的 656.25 ms 波动，也不能借它给 GUI 慢窗补造 CPU 分解。实际负载扰动、全进程生命周期和根因归属均未通过。正式修复未完成。

## 三次尝试完整保留

1. `diagnostic01`：PowerShell 将模型 stderr 的 INFO 日志转换为 NativeCommandError，命令提前返回。外部查询无目标进程，只有锁、无最终工作/计量结果，工作进展未知；不能把该次算作成功或认定没有执行负载。
2. `diagnostic02`：启动器已修正，但旧入口固定读取 `plan01.json`，与包装器的新案例编号不符。子入口在创建案例目录及工作前拒绝，`accounting02.json` 保留零次读取及 AssertionError。属于适配错误，不是性能证据。
3. `diagnostic03`：为旧入口创建独立 `child03/plan01.json`；包装器在启动前验证双方案例编号、所有工作身份字段及冻结源哈希。完整运行通过，线程集合验收失败，结果如上。原两次失败未覆盖、未并入任何统计，也没有在相同冻结批次中追加样本以凑通过。

`launch.py` 直接用 Python Popen 管理子进程及原始 stdout/stderr，先保存 PID/命令，超时只记录观察超时和存活状态，不杀进程、不重启。四项 Windows 测试验证 INFO stderr、非零退出、超时保留活进程和拒绝覆盖旧窗口；全部通过。首次尝试的 PowerShell错误保留在 `execution01.json`。
