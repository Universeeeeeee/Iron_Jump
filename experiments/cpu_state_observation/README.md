冻结状态规则为准备阶段 ≤3500ms 快、≥4300ms 慢，中间值单列；这是从历史共同准备代理提出的探索性分类，非现场症状分类。四窗全部慢，**`both_states_observed=false`，本轮不能判别慢/快状态的系统差异。**

每窗准备和消费阶段各有 4 个完全落在阶段内的有效 1Hz 区间，消费完成后的模型尾部各有 2 个；均满足冻结的最少 2 区间要求。相邻采样边界不得超过 1.5 秒，单次采集边界不得超过 50ms，跨阶段及无效值排除。全部 341 条原始记录保留；每窗最大采集墙钟约 3.78–5.55ms。这个开销不等于完整观察器扰动，更不代表原 3%/1% 门槛通过。

上述 12 个阶段的系统 `% Processor Performance` 中位数均约 **99.998%–100.004%**，队列长度中位数均为 0，选中区间的电源来源均为 AC。这里是操作系统提供的全系统聚合值，**不是直接测得的 GHz、睿频关闭证明或节流原因**。总忙碌率不代表任一具体核心空闲；队列中位数 0 不排除短暂调度等待；没有外部进程责任分解。准备线程 CPU 接近墙钟，进一步约束了“主要是等待导致准备慢”的解释，但不区分实际执行路径、缓存/内存及 CPU 交付速度。

结束后只读查询 `power_after01.json`：活动平衡方案，AC/DC 最小处理器状态 5%、最大 100%，性能提升模式索引 2。策略配置允许提升不代表硬件实际交付；它与近标称 PDH 读数不能自行闭合成频率根因。未读取硬件性能寄存器、温度/功耗限制原因或这些历史快窗的同类计数，不据此下定论。

## 方法与失败保全

`probe01.jsonl` 是先前 3 秒探测的原始两条记录。首条速率无效，这是缺少前一计数基点的情况；第二条全部有效。初始本地断言错误地要求 3 秒一定生成 3 条，忽略注册计数器耗时而失败。`probe_review01.json` 保留该失败及重新解释，没有重跑或补造探测数据。正式观察按完整有效区间而非预计条数验收。

运行前 Windows 8 项语义/门禁测试和原生结构大小检查通过，计划与源文件哈希冻结，远端门禁验证后才启动。分析器在查看任何工作窗口结果前绑定哈希；4 项分析测试覆盖跨阶段、无效读数、长采集区间和超过标称值不截断。`workload_changes01.diff` 明示相对原工作仅增准备边界和默认 OpenCV 配置核对。

36 文件归档逐项 SHA 核验，归档 SHA256：`6fc441f801f93db5691e25eba05992d842ba16d2454362ffa41d7673a6e24432`。4 个工作进程与观察器均正常退出，5 个锁保留。458 个正式文件、依赖、输入、模型、媒体、原 NumPy/Python/OpenCV 二进制未变，WPR 未记录，采样间隔 10000×100ns。

## 决策

这次预算已用完，不能再以同协议等待快态出现。保留“慢态以实际线程 CPU 时间为主、同窗未见持续总队列饱和”的有限结论。下一项验证必须有独立于 PDH 标称性能读数的 CPU 执行能力证据，或者一个预先定义且能恢复的单一状态干预；不能直接调节多个电源/调度设置，更不能把原单线程 OpenCV 失败候选重新当修复。

根因、实际负载扰动资格、原 GUI 1000Hz pending/contact→paint 修复均未完成。正式程序保持不变。
