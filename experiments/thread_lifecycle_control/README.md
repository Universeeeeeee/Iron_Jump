# 短命线程生命周期控制：三个预定线程全部观测到

单个冻结合成窗口，三个线程依次创建、执行约150ms算术工作并退出；它们全部发生在前后两次线程枚举之间，且不出现在两端枚举中。没有重复窗口。

## 结果

| 顺序 | TID | 线程 CPU ms | cycles | 生命周期与计数关系 |
|---|---:|---:|---:|---|
| 0 | 22144 | 156.250 | 359998800 | 实际 Start/End 包围计数窗口，且完全位于两次枚举之间 |
| 1 | 23072 | 156.250 | 358858320 | 同上 |
| 2 | 22376 | 140.625 | 357002880 | 同上 |

GetThreadTimes 的创建时间在每个线程前后保持一致，PID/TID 与 ETW 载荷对应；执行块计数非零、结果正确、线程 join 完成。整个目标进程共7个TID有生命周期记录，其余线程没有独立控制角色，不赋予来源。

ETW header/consumer/buffer loss均为0。原始QPC与转换时钟对所有fixture锚点的最大残差为0ms，通过原1ms时钟门槛；这表示落在观测括号内，并非宣称物理误差绝对为零。perf_counter与QPC的区间映射还验证了整个已知生命周期位于两次枚举之间。

只启用 ProcessThread 与 Loader。没有 SampledProfile、CSwitch、ReadyThread 或 StackWalk 事件。旧CPU栈、等待栈及扰动质量门槛没有修改。

## 清理与证据

复用原 `native_stack_capture/record.py` 的会话所有权及失败清理逻辑，单独指定生命周期profile，未改旧控制器。唯一会话停止已确认，WPR外部状态确认未记录；采样间隔前后均为10000×100ns，没有设置调用。所有fixture线程退出、句柄关闭、目标进程结束；独立外部查询无相关进程。阶段锁保留，原始ETL留在Windows。

读回事件、metadata、fixture和record均与远端独立Get-FileHash一致。14项旧清理故障测试和5项新事件分类测试通过。

## 保留的问题

- 编译器首次将绝对路径错误解析到 `e:\ReadStacks.cs`，在启动采集之前失败。记录保留；改成同源字节、独立目录相对文件名后编译，没有发生前一轮采集。
- 首版审核器将所有PerfInfo事件都视为禁止。实际只有4条opcode34/v0文本标记：`Wpr_Initiated_Rundown`、`General`、`No description provided`、`Nativelifecycle`。首版失败记录与代码保留；新版仅允许该类且逐一验证实际载荷，仍拒绝采样、栈、CSwitch/ReadyThread和未知PerfInfo。没有放宽数值门槛或重采。
- 当前只验证三个已知短命线程；没有实际发生TID再利用的控制。纯逻辑生命周期解析仍将再利用分成多个生命周期，不能将同TID跨时段直接合并。
- 起始地址字段尚未验证。本次不能据此命名线程所属库、函数或GIL持有者。
- 生命周期采集的实际负载扰动尚未校准；此通过不授权任何CPU/GIL定量归因，也不能回填最近未录ETW的固定模型窗口。

## 接下来

已有工具能够观测两端枚举漏掉的已知线程。下一步需要把线程来源字段与独立系统接口交叉核对，再为固定原模型任务冻结生命周期与计数联合诊断方案。必须继续保留未解释余额及全部质量失败；正式程序、设备、人体和GUI A/B均未改动或启动。
