延续 `aeef772` 的唯一候选：在独立实验进程保持原始并发工作，仅调用 `cv2.setNumThreads(1)`，与原配置 8 对照。固定 6,824 帧原始消费链和 220 次真实模型调用，没有新增人体、设备或 Run 测试，也没有修改正式程序。用户已授权该单变量离线因果对照。

## 交付与语义证据

`plan01.json` 冻结 default/one 两个交付窗口。生命周期 ETW 中，实际工作区间新建且入口归属于 `cv2.pyd` 的线程由 **3 个降至 0 个**；ROI 没有无法分类的 Start。整条 trace 各有一个启动阶段入口无法分类，保留未知。这里证明本候选改变了观察到的线程创建行为，不证明全部运行线程归属或热点份额。

两窗的 220 张实际 resize 输出逐像素哈希相同（640×360、uint8），原始模型返回与完整消费语义一致。生命周期零丢失、原 1ms 时间门槛通过。详见 `delivery_review01.json`；原始 ETL 保留在 Windows，派生归档 SHA256 为 `109311ab13d776883d676284ed723a5c029779c04ff24c5ad0fb5307b5c940c4`。

**前置测试执行失败不能改写为通过。** Windows 部署漏传既有 `test_record_cleanup.py`：8 项交付测试通过，清理测试导入失败。外层命令没有 fail-fast，仍启动了两个冻结窗口。这是本次执行控制错误，记录在 `preflight_failure01.json` 与 `windows_tests_failed01.stderr`。之后只补传测试文件，确认运行源码未变，22 项 Windows 测试在采集后通过；它们不是前置通过证明。两个窗口均保留，未重新采集替换。

## 对根因判断的影响与下一步

**停止推进 OpenCV 单线程作为修复候选，不进入该候选的 GUI 验收。** 实际线程交付已变化，但在这个固定并发协议中，收益不足且整组工作明显变慢；不能把观察到的 OpenCV 线程直接等同于主要积压根因。

上一阶段同批工作“重叠/不重叠”的方向性证据仍成立，但不能把那批约 25.4% 的差异与本批 1.57% 相减分配责任。两批运行状态不同，本批默认消费者约 4.94–5.01 秒，旧批后面三次默认并发约 2.86–2.98 秒；这种跨批状态差异仍未解释。

后续应优先用现有固定工作记录审查慢/快状态的消费 CPU、模型调用与共同阶段边界，收窄尚未控制的运行状态因素，再决定一个新的机制检验。不能凭本次失败转而认定 GIL、GUI、NumPy 或设备为主因，也不同时尝试多项优化。最终仍需回到原 GUI、1000Hz 输入、pending 和 contact→paint 症状验证；本轮没有这些终点，未证明现场修复。历史栈完整性与 3%/1% 失败保持。
