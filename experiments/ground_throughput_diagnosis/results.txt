分支：codex/ground-throughput-diagnosis

状态：诊断完成。回放及现场复现、完整语义核验完成；阶段/GIL/Qt 定量拆分未达到证据门槛。

结论的有效范围

目前证据足以确认：GUI 与光束消费线程存在双向 GIL 竞争，接触密集时会出现消费不足；
还不足以给 DeviceQualitySession、GroundStabilityFilter、两种 Processor 分配可信的基线 CPU 百分比，
也不足以把 Qt/Windows 调度与 GIL 等待分别量化。原 NumPy 保留，本轮没有实施性能重构。

必须先说明的测量问题

1. 原有同源完整 GUI 回放在 offline 分支把整个相机 panel 设为 disabled。
   这与正式预览的 enabled 状态不同。Qt QLabel 在 disabled 状态用 QIcon::Disabled 生成图像。
   原生快照抓到 GUI 的 QCommonStyle::generatedIconPixmap，实际截图预览也为灰度；
   因此旧完整回放包含额外的禁用图像生成负载，不能直接外推正式现场成本。
   新 enabled_replay.py 只在实验入口改一行，原回放、正式源码及原 NumPy 均不改。

2. 两个模式的低扰动探针 A/A 均未通过预先冻结的阈值。
   六对/模式，MD、DM 交错，抽样偏移 0/11/23/37/49/61；所有慢轮均保留。
   D−M 的配对中位数：
     跑步：消费 fps −0.195%；队列年龄斜率 +18.284 ms/设备秒；脚印 P95 +48.682 ms。
     走路：消费 fps −0.0273%；队列年龄斜率 +5.633 ms/设备秒；脚印 P95 −7.340 ms。
   阈值分别为 3%、5 ms/设备秒、25 ms，任一超限即失败。
   上述配对差异也可能含快慢状态与噪声，不把它全部解释为探针造成的净开销。
   不能只看 fps 平均变化小，就接受阶段计时。stages.csv / grouped_stages.csv 仅是 D 条件下
   的探索记录，不是原程序各阶段占比，也不是优化收益。修正 panel 状态的 E/O/E 不是新的 D/M 校准。

3. Windows thread_time 声明 100 ns，但 2000 次约 50 us 忙循环里，1998 次增量为零，
   另外两次各 15.625 ms。该时钟无法支持逐调用 CPU 归因；墙钟减它不能算 GIL 等待。
   QueryThreadCycleTime 使用 PyDLL 获取原始周期，不能转换成 CPU 毫秒。
   抽样树对直接子调用相减，逐树验证墙钟、粗 CPU 计数和周期的加法守恒，避免嵌套重复计算；
   观察成本仍包含在抽中帧，不能机械扣除空调用下限。

可复核的证据排序

第一：GUI 和消费线程争夺 GIL，机制已独立证实，持续时长和吞吐损失比例尚未测定。

跑步单次原生快照：GUI 持有 GIL，原生路径 generatedIconPixmap/QLabel::paintEvent，
对应 AnnotationCanvas.paintEvent 的 super 调用；消费线程停在 NumPy 返回 Python 的
PyEval_RestoreThread / WaitForSingleObjectEx，Python 顶层为 RuntimeBeamEvidence.observe。
走路单次快照相反：消费线程在 WalkingProcessor._observe_ownership_groups 的 list comprehension
持有 GIL；GUI 从 Qt 回调进入 Shiboken::GilState / PyGILState_Ensure 等待。
这是双向竞争证据；快照命令用时不是等待时长。原生导出符号有近邻名称，不能据此编造具体内部函数。

改为 enabled 预览后的独立 py-spy GIL 持有者采样仍有大量 GUI beam_layer Python 循环样本：
  跑步实际捕获 220 栈，GUI 108、消费 80；beam_layer 45/46 行分别 25/20；采样错误 37。
  走路实际捕获 595 栈，GUI 271、消费 211；上述两行分别 67/49；采样错误 121。
这些是实际捕获的栈数。nonblocking 采样有竞争和缺失，不能转换为时间占比或持锁百分比。
回放骨架有真实有效节点、连线绘制和截图证据；不能把 QLabel super paint 全部归到骨架。

第三：下游质量与滤波逐帧工作、接触归属维护均有实在计算，但尚不能可靠排序其基线独占成本。

DeviceQualitySession.on_frame 包含运行时证据窗口与每帧判断；RuntimeBeamEvidence 与 quality 不能
分别计算 inclusive 后相加。GroundStabilityFilter 包含 mirror guard、滤波及渲染输出；
Walking/RunningProcessor 包含 clusters/groups、ownership/commit/publications，summary 又嵌在
session 发布路径里。原生快照确实抓到 NumPy GIL 恢复等待和走路 ownership 的 Python 持锁；
不能把一个 NumPy 栈的墙钟全部叫 NumPy 运算慢，也不能将 summary 的嵌套成本重复算给 processor。
查看 grouped_stages.csv 时只读互斥 exclusive 分组，且仍限 D 条件，不按它宣称正式阶段占比。

第四：Qt 调度仍是候选因素，当前不能独立定量归因。

inbox 每次取至多 20 帧，4 ms 预算仅在一块处理完后检查；pending 时 timer=0，否则 5 ms。
一次块可以超过 4 ms。D 的慢轮墙钟多数落在 drain 内，有积压时 drain 之外间隙通常较小，
提示关注回调内部的计算/GIL；但 D 已校准失败，不能拿该覆盖率当基线 CPU 占用或排除调度。
M 只有批次完成点，无法分离进入回调前的 Qt 延迟和回调内部等待。

  走路：物理 10、confirmed_contacts=10、valid_touches=9、valid_steps=5。

    未发布的末步不能记为零延迟，亦不能据此声称 10 步均在 365 ms 内显示。
