一、要回答的问题
融合 RuntimeBeamEvidence 与紧邻告警判断中的单帧数值操作，能否在真实 Windows GUI 回放负载下减少积压和脚印延迟？
本实验只改变数值实现。正确性通过后分别判断“重复改善”和“持续实时达标”，不得合并表述。

二、实验基线先行
当前工作目录有大量未提交文件，新工作区仅包含 Git 提交，不能直接替代已验收版本。
实施前从原目录和旧回放包重建真正执行的基线，保存所需源文件、补丁、依赖版本与输入哈希。
基线固定为已验证的 Canvas + 归属快照去重 + 稳定帧快速路径 + 原 Runtime + 原 Inbox，几何缓存相同。
旧入口：exports/canvas_latency_20261015/replay_final.cmd；探针：runtime_gui_probe.py。
原入口有 Windows 绝对路径和动态模块加载，必须核对实际运行路径，不能仅复制命令或依据 Git HEAD。
保留主目录现有改动；仅将本实验必需的基线源码带入实验工作区，基线导入与后续优化分别留差异记录。
source_reference.json 只记录制定计划时的源文件哈希，不代表基线已经重建或验收。
先复现一组无优化 A/A 回放，确认输入、算法、报告和脚印一致，检查探针是否显著扰动。
验证旧基线的依据是源码与数据身份、行为等价和重复测量；不要求新机器或新时段的耗时恰等于旧数字。

三、实现边界
Python 保留：SensorFrame 校验、stream/layout/采样连续性、deque 生命周期、异常重置、质量记录及 Qt 信号。
编译函数尝试融合：XOR、counts/transitions 加减、过期项扣除、阈值判断及掩码变化比较。
每次仍只处理一个采样；不改 Inbox、时间预算、线程、滤波阈值、状态机、报告结构和批次接口。
初始帧无 previous、无过期项、窗口未满等分支必须明确；整数类型和阈值比较沿用原语义。
历史 changes 每帧独立拥有数据，历史 bits 的底层字节保持有效；禁止窗口引用被复用的可变暂存数组。
上一帧告警掩码保留独立快照；返回新掩码前不得破坏比较对象。
告警阈值与状态变化仍逐采样判断，不延后告警，不只比较最终报告。
第一轮不做 fastmath、parallel 或其他编译选项优化。

四、三个候选
A：冻结的原 NumPy 实现。
B：单帧融合，nogil=False。
C：与 B 同一函数体、输入输出及数据结构，唯一差异是 nogil=True。
三组使用相同 Windows Python/NumPy/Qt/Numba 环境和输入；避免把依赖版本变化当成优化收益。
三组进程均在测量前导入并预热编译函数，预热使用独立临时状态，随后销毁并新建正式会话。
记录实际签名、nopython 编译结果、nogil 设置、版本、执行文件哈希和预热时间。
单独检查首次启动及缓存不可用时的表现；首次编译耗时不混进稳态测量，也不从部署评估中隐去。
Numba 留在实验依赖中，正式 requirements 暂不新增。

五、正确性门槛（必须先通过）
对既有真实录制、六份历史步跑数据及合成边界逐帧对比 A/B/C。
覆盖 1/2/4/8 段；有效布局切换、stream 切换、采样跳号/回退、掉帧标记、无效长度/valid_bits、质量标记。
覆盖首帧、窗口刚满、首次滑出、长期滑动、遮挡持续阈值、变化次数阈值，以及告警出现后消失。
特别保留历史数组并继续推进多个窗口，检查历史内容及告警快照没有被后续帧改写。
核对每帧返回值、counts、transitions、healthy_samples、窗口内容、previous、异常掩码及全部告警区间。
同时以独立简单计数 oracle 核对合成数据，避免只由同源的两份实现相互证明。
核对原始采样顺序、wire、bits、采样号、事件确认/发布位置、完整算法摘要和 TestReport。
仅对已经独立核对的回放主机时钟字段采用显式转换；不得忽略未知差异。
任一语义差异立即阻止性能采用；完整 GUI 性能轮不启用逐帧深度比较或 cProfile。

六、完整 Windows GUI 短窗口对照
复用原 14,404 帧窗口、97705 固定启动、原光束接收节奏、相机录制、实际推理、骨架及脚印绘制。
固定 Canvas/处理器/滤波/几何缓存、窗口尺寸和推理设置；每轮独立原生桌面进程。
正式顺序预先固定为 ABC、ACB、BAC、BCA、CAB、CBA，共 18 轮，每组 6 轮。
每组三轮作为一块，B/C 分别与该块 A 比较；所有反向结果保留，不按结果补删或改变顺序。
记录实际收到/消费速率、接触窗口队列年龄斜率、队列峰值与末尾值、接收及计划发送至 paint 的 P95/max。
同时记录推理/解码/预览帧数与 GUI 四项耗时，防止降低视觉负载或拖慢发送伪造改善。
保留从接收到确认、发布、visual、paint 的分段观察；paint 返回不称为物理屏幕呈现。
输出每轮源码/输入身份、原始数据核对、报告、事件时间和原始测量，不只保留中位数。
排除仅限事先定义的启动失败、数据身份错误、观测文件损坏或外部中断；保留记录和理由，正常慢轮不排除。

七、预先固定的判定规则
以下数值是本实验工程门槛，不宣称行业标准；开始正式性能轮前写入机器可读 trial_plan.json 并冻结哈希。
重复改善：B 或 C 对同块 A 至少 5/6 块 P95 更低，配对降幅中位数至少 10%。
同时要求接触消费 fps 中位数不降低、队列年龄斜率中位数不增加、GUI 耗时中位数增幅不超过 5%。
实时达标另判：候选全部 6 轮 P95<=150ms、max<=250ms，队列年龄斜率每轮<=10ms/设备秒且中位数<=5。
短窗口通过不能单独判定持续实时达标，还须通过下一节的长负载与数据一致性检查。
B/C 都通过时优先比较完整负载队列与延迟；若差异不足以区分，优先采用不释放 GIL 的较简单候选。
只有微基准改善、结果不稳定或语义差异时，本轮不合入；保留失败证据，另立下一热点调查。
短窗仅重复改善但实时门槛未通过时，结论为“局部改善、未解决积压”，不自动扩大本轮范围。

八、长负载与现场边界
先建立连续 60 秒及 5 分钟压力输入；三组使用同一输入，保留每帧状态推进。
拼接必须生成连续采样号和时间，明确空场接缝及会话状态；禁止靠反复重置质量窗口或状态机降低负载。
真实片段循环与合成持续负载分别标注，不冒充更多独立真人样本；保存构造方法及输入哈希。
60 秒三组各跑 3 轮；5 分钟阶段验证 A 与短窗口胜出候选，各 3 轮，交错执行。
以足量待处理输入另测追赶能力，实时 1000Hz 播放不用于证明 >=1200fps 的处理上限。
长稳门槛：无丢失、同源输出等价；稳态队列年龄斜率<=1ms/设备秒，队列不呈逐段抬升趋势。
斜率以启动后固定窗口计算，报告前后半段队列中位数/峰值及停止前未处理数量，避免只看 EOF 排空。
>=1200fps 为额外工程余量目标，单列结果；达不到不伪称有该余量。
已有数据足够完成本轮原型筛选，无需先安排真人。回放通过后再做真实设备、相机驱动、跟随、推理、录像并发现场复核。
现场以实际步行、跑步和连续重复通过确认；现场未完成时，只标记离线回放通过。
