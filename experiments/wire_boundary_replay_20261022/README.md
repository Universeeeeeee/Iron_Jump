## 本轮回答了什么

上一轮重放跳过了协议解析与组帧。本轮把保存的 payload 编成逐段 DATA 包，
经过原 `ProtocolParser → UsbWorker._on_frame → SensorFrameAssembler → _GroundFrameInbox`，
再进入原消费者与真实 GUI 控件。CRC、拆包、逐帧内容与最终报告分别验证。
八段包及 2048 字节读取均为合成控制，**不代表现场真实分包与读取时序**。

实际代码边界：

| 位置 | 工作与限制 |
|---|---|
| `hardware/receive.py:start_auto_read` | 现场 DLL 读取后，Python 读线程同步解析并调用 worker；DLL 时延和原始到达模式未留存 |
| `hardware/usb_worker.py:_on_frame` | 在读线程内组帧、发射完整帧信号；生产关闭 legacy 信号，不能再把兼容 HEX/列表生成当作嫌疑 |
| `ui/session_controller.py:_GroundFrameInbox` | DirectConnection 入队；测量线程定时消费。进程化后读取线程和消费者仍共享子进程 GIL |
| `ui/embedded_camera_panel.py:_render_frame` | 主 GUI 线程执行骨架叠加、颜色转换、缩放及 QImage/QPixmap 更新；本轮未覆盖这些负载 |
| `vision/live_walking.py` / `vision/service.py` | MediaPipe 服务位于主进程后台线程；50ms 推理请求间隔。仍可能竞争主进程 GIL/整机 CPU，尚无本轮现场耗时证据 |
| `ui/measurement_process/client.py` | 主进程后台线程收包，GUI 定时分发；现场历史没有逐个脚印的完整收包至绘制时间 |

## 对根因判断的推进

多进程确实可能通过隔离 GUI/视觉 GIL 竞争改善消费者。本轮加入原协议处理后，子进程仍没有复现现场秒级积压；
尚无证据把 IPC 本身判为现场主因，也不能据此排除真实读取模式或带视觉负载时的 IPC/GUI 积压。

待闭合的两处差异是：真实 USB 字节到达/解码完成，以及开启真实视觉/SDK后的主进程接收/分发/绘制。
历史文件没有前一项，屏幕录屏也不能替代原始相机帧或真实 SDK 工作量。
下一次若获准现场补证，只需在这些边界对同一 event_id 加入低频时序记录，并同时保留原字节到达批次；
当前不触发现场采集、不改变默认后端、不改算法。
