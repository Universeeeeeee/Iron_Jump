# 新冻结边界：三个线程控制达到预期，生命周期缺口得到实证

`plan02.json` 对应 `inventory02.py` / `run02.py`。原 `plan01.json`、源文件、失败结果和锁全部保留。新版本只改变计量安排：枚举与句柄构造在工作开始门之前完成，计数读数结束后再枚举；单次读取仍为 1 ms 上限，计数组仍为 10 ms 上限。原失败没有改成通过。

## Windows 实测

| 控制 | 开始/结束计数组 ms | 进程 CPU ms | 已持有线程合计 CPU ms | 预期行为 |
|---|---|---:|---:|---|
| 两个稳定计算线程 | 0.0760 / 0.1095 | 2000 | 2000 | 保留线程计量通过 |
| 已持有的线程工作后退出 | 0.0576 / 0.1715 | 2000 | 2000 | 因退出和枚举变化拒绝 |
| 两次枚举之间创建并退出 | 0.0466 / 0.1174 | 2000 | 0 | 不得宣称完整覆盖 |

所有控制的算术执行已确认。第三个控制的前后枚举及保留句柄均稳定，但发生了 2000 ms 未纳入线程合计的 CPU 工作。这直接验证了“前后线程列表一致”不足以证明全程线程覆盖。第二个控制即使 CPU 恰好完全相加，也仍拒绝生命周期验收，避免多个相符数值掩盖已退出线程。

独立复算验证：完整三个窗口、计数/生命周期结果、旧源与计划哈希、每个工作线程的实际执行区间均包含于新计数边界，枚举确实位于进程计量之外。提前退出窗口只接受预定的退出/枚举变化失败原因，其他质量失败不会被负控制掩盖。

## 枚举成本没有消失

每次枚举仍为 41.5–45.3 ms；对应调用线程 CPU 计费约 31.25–46.875 ms。句柄构造和前后枚举的独立区间与 CPU 读数保存在原始结果中。这些成本只是移出了门控的工作计量区间，其缓存、预热和系统状态影响没有消除，不能据此宣称真实应用扰动小于 3%。

短命线程缺口不能靠“进程 CPU 减去已知线程 CPU”精确分配：差值可能同时包括未知线程、不同读数边界、观察器自身工作和 OS 量化。尤其不能命名为 GIL 等待、线程池 CPU 或模型内部计算。

## 验证状态与下一步

七项逻辑测试在本地及 Windows 启动链通过，新增检查确保快速计数函数不调用系统枚举。Windows 三个控制完整完成；所有创建线程退出，句柄关闭。外部终态查询无 Python/observer 进程；新旧结果和计划都与远端 Get-FileHash 一致，两个尝试的锁保留。

工具现在可提供“已持有且持续存活线程”的计量，尚不能提供全进程生命周期完整覆盖。用于真实固定任务前，应保存未解释余额并验证原生池线程是否新建或退出；若要声称完整归属，还需通过单独校准的线程生命周期事件记录证明窗口内没有遗漏。不能只把新的快速枚举边界接入 GUI 后宣布根因。

本轮仅合成控制，无设备、人体、真实模型、GUI A/B 或正式程序修改。旧 3%/1% 与原生栈验收失败保持，根因及正式修复尚未完成。
