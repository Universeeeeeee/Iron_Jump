# 正式单 USB 现场复现与无人原生跟踪校准

2026-10-16，独立分支 `codex/single-usb-field-reproduction`，基于 `210d86a`。本轮没有性能优化、绘图 A/B、阈值调整或正式程序修改。原 NumPy、原绘图器、已有 beam_layer 候选均保留。

## 结论与证据等级

1. **走路接触密集段存在数据已经入队、消费者处理落后的直接证据。** 一次去程中，密集设备秒 11–16 的探索性聚合：实际入队约 1008.27 fps，完成约 916.45 fps，最老待处理年龄达到 706.37 ms，待处理最多 710 帧。不能用“仅上游迟到”解释这段已有队列积压。尚不能区分独占计算、GIL 竞争、线程被调度等待或观测器开销。
2. **这不是稳定重复复现，也不是冻结整窗门槛通过。** 现场各模式只有一次。冻结分析 `analysis.json` 中走路和跑步的宽窗口判定均为 false；它包含空场、接触间隙及恢复期，且晚期光束 64 脉冲扩展了 contact_span。`dense_diagnostic.json` / `phase_metrics.json` 的局部聚合是事后诊断，原结果没有重写。走路密集窗口的最大采样间隙 279.69 ms，超过 250 ms 的连续性要求；其中 heavy 连续观测段为 4.84 s，不能把整个 5.78 s 观测窗称为无缺口的持续状态。
3. **初始 5 秒空场没有重现此前严重持续消费下降。** 两轮初始队列最老年龄最大分别 49.24 / 20.85 ms，没有满足持续不足条件。这不能证明密集走跑正常，也不能解释旧双输入异常的全部原因。
4. **跑步负载覆盖不足。** 原始录像显示约第 11 秒人体已部分离开相机画面，第 12 秒所抽原始帧中无人；正式计数也显示接触阶段骨架绘制中断。SDK 开启不能替代实际绘制量。该轮不能作为持续全身跟踪/骨架负载下的通过证据。
5. **无人原生调度记录的冻结 OFF/ON 校准 6 对全部通过。** 仅覆盖空场、预览与真实录像、SDK 开启且实际有效骨架绘制为零的条件；不覆盖有人密集负载，不校准现有批次留存/SDK 日志观察器自身开销，不证明优化收益或 GIL/GC 根因。

## 实验拓扑和条件

Windows 根目录 `E:/OptoJump/IronJump-single-usb-field-20261016`，独立于既有实验目录。默认唯一真实输入：`UsbWorker → _GroundFrameInbox → DeviceQualitySession → GaitEngine`，只有一个 CyUsbInterfaceReader。没有固定回放或第二路 USB；使用正式 NumPy 和正式 `GroundChannelWidget.paintEvent`。

相机原生 1920×1080 / 100 fps 请求与连接信息一致，保存原始 MJPEG+CSV（不是桌面录屏），`preserve_raw=True`。SDK 全身跟踪开启，正式 Qt 下肢骨架实际绘制另计数。支持的停止配置改为 Software command，仅用于保留离开后的空场，其他走跑参数沿用默认值。

QueueProbe P 与前轮逐字节一致。每批留存既有 immutable SensorFrame 引用，停止后序列化；保留 SDK 既有事件，实际绘图计数、1 Hz GUI 状态及首次确认脚印 paint 完成时间。没有嵌套阶段计时，没有新增高频 Python 调用树。上述新增档案留存和 SDK 记录开销尚未独立校准，长准备阶段也会增加内存负载。

`field_walk_01` 仅为失败准备：确认框不可见、没有正式 armed；watchdog 结束并关闭 SDK，排除于性能样本。实验窗口固定顶部控件、将 ExecutionView 放入滚动区后，屏幕几何和现场确认均核对。旧准备版本保存在 `harness_versions/preparation01/`，没有覆盖其证据。正式两轮使用同一 revision 2，随后未修改冻结运行代码。

## 原录像和实际负载核验

原生相机录像与 CSV 均闭合，两轮 writer drop 为零，关闭时队列为空、无 native 错误。走路原视频约 3.97 GB，跑步约 2.10 GB。完整文件留在 Windows；Mac 保存 CSV、精确原 JPEG 抽样及元数据。`native_inspection.json` 使用 record-start perf 前后括号中点对齐，没有漂移校正，不用作精确步态落地标签。

只检查去程。走路正式 0/5 s 可见近端人体，13 s 去程全身可见，17 s 已在远端；29 s 回到电脑旁不作为通过光栅。自动准备门槛曾对遮挡/杂乱画面产生数值有效结果，故不能单独证明全身入镜；后续真实原录像和现场确认是独立交叉证据。走路密集段实际骨架约 18–23 次/s，常见 10 节点/10 连线。

跑步 5 s 近端人体可见，10 s 开始去程，11 s 抽样人体部分出画，12/13 s 抽样无人。SDK 正式非零速度调用分别走路 309、跑步 38 次；SDK `sdk_call.started_at/returned_at` 为调用本身的 perf 时间，外层 host_ns 是稍后的 GUI 接收时间，两者不能互换。跑步持续骨架负载条件未满足，不把 `analysis.json.valid_field_protocol=true`（仅基本采集/空场/尾段）当作完整负载通过。

## 完整性与正确性边界

`verify_capture.py` 离线检查通过：wire 经独立 NumPy little-bit 解码及布局重排与原 bits 完全一致；设备/帧计数连续、无 dropped_frames_before 或采集 issue；正式原档逐帧对应 retained SensorFrame，原档 SHA 相符；一个真实 reader、最终 pending/unfinished 均为零、SDK 停止。

事件 audit 与完整报告一致；质量快照与报告 beam_quality 一致，质量事件没有截断；正式可视时间线与原处理器时间线按正式坏点有效位规则转换后完全一致。没有修改/归一化原始报告或计数。报告不含重复巨型 export_frames/export_timestamps 字段，其相同内容保存在独立原档 NPZ。现场非确定性采集不是跨轮语义等价测试。

现场口述标签单独保存在各轮 `human_observation.json`：

- 走路：10 步、右脚先入；报告 touch_count=10、active publications=10、已绘制 contact=10，valid_steps=7。不同有效步/周期/间隔计数需要独立语义审计，不能仅凭 10≠7 确认算法错误。
- 跑步：8 步、左脚先入、预览 6 个脚印；报告 touch_count=6、active publications=6、已绘制 contact=6，valid_steps=3。相对口述的缺口在发布流中已存在，不能仅归因于界面漏绘。需独立以原光束与去程录像逐事件核验。

配置 starting_foot 保持原默认 Not defined，没有事后按口述重写。末步漏发布与有效步间隔问题不混入本轮吞吐结论。

## 无人原生调度校准

完整冻结协议、逐对结果和交付事件校验在 `../single_usb_native_calibration/`。每条件新进程，20 s 正式段，主比较窗为 host 3–19 s，8 s 间隔；三对走路配置与三对跑步配置交错 OFF/ON，保留全部 12 轮，没有为通过而重跑。

WPR 唯一实例 `IronJumpSingleUsbSchedule`，仅 ProcessThread、Loader、CSwitch、ReadyThread，不采 CPU 栈或 Python 调用树。2 次原生 GetThreadTimes 和 FILETIME/perf 括号仅在正式起止边界采样，CPU 比较范围约完整 20 s，另列于主比较窗。

所有 6 对满足冻结消费差≤20 fps、队首年龄 P95 增量≤20 ms、预览比[0.9,1.1]、原生录像帧率比[0.95,1.05]、消费者 CPU 增量≤10%，并满足档案完整、空场≤1%、writer 无丢帧等条件。实际消费差 −0.508 至 +0.160 fps，队首 P95 增量最大 +0.547 ms。首对 CPU ON/OFF≈0.589，提示跨进程/机器状态变化，不能当作跟踪改善性能的证据；冻结 CPU 规则是一侧增量限制，不是对称等价检验。1000 Hz 输入饱和也不能证明存在余量。

6 份完整 ETL 的全扫描摘要确认 CSwitch/ReadyThread 存在，事件与 header BuffersLost 均为零。安装的 tracerpt 对 CSwitch v5 仅提供二进制载荷，因此当前验证止于“确有调度事件且无丢失”，没有输出可信的 Running/Ready/Waiting 时长。XML 显示时区 +07:59 与系统 +08:00 不一致，后续须用原始 FILETIME/perf 括号独立核验对齐。头部抽取导出器独占文件，首次尝试写入期间读取失败；离线工具改为关闭后读取完整 header，完整 ETL 与独立全扫描摘要未变。解码问题没有触发任何重新采集。

冻结宽窗条件未触发原有“整窗通过再跟踪”门槛；本轮无人校准是基于局部已入队积压证据及用户随后明确授权另行开展，不把它表述为原门槛通过。它仅验证轻负载跟踪开销，**没有有人走跑 ETW**。

## 按证据排序的归因与下一步

| 解释 | 当前证据 | 尚缺验证 |
|---|---|---|
| 密集走路时消费者服务不足/不能及时执行 | 已入队≈1008 fps、完成≈916 fps、队列与接收年龄增长；最强直接证据 | 相同负载重复，以及原生线程 Running 与 Ready/Waiting 分解 |
| 有人跟踪/骨架/SDK竞争与接触处理共同增加负载 | 同轮空场较轻、走路密集段骨架持续；跑步负载明显不同 | 控制输入与实际绘制量的配对；不能据此直接指定 GIL/Qt 或某个函数 |
| 批次引用留存、长准备期和 SDK 事件保留造成额外压力 | 本轮明确存在这些实验观察器；准备期较长 | 独立 under-load 观察器 A/A；无人 WPR OFF/ON 没有校准它们 |
| 上游/USB/线程交付迟到后追赶同时存在 | 应用接收也存在抖动；设备计数连续不代表均匀交付 | 更低层交付与已校验时钟对齐；本轮不能证明没有上游问题，但不能仅以它解释已有积压 |
| GIL、GC、某个 Processor/质量/滤波函数是根因 | 尚无独占成本或原生调度支持 | 调度状态本身也不能独立证明 GIL/GC，后续需有针对性的互证 |

本轮不建议实施任何新的最小性能优化或移植 beam_layer。最小下一步是**先离线验证现有 CSwitch v5 解析及时间对齐，并以已保存的 GetThreadTimes 交叉核对 Running 积分；再在下一次有人条件下，原拓扑、持续有效骨架、短准备期，校准并重复记录密集走路**。本轮无人校准通过不能替代负载校准。只有区分消费者 Running 占用与 Ready/Waiting 等待后，才选择下一处最小改动。无需今晚继续人体测试。
