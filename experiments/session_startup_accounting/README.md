## 仅补少数边界

复用已验证的共同 `session_local_baseline/gui.run`、原Controller/QThread/NumPy/滤波/Processor/renderer、真实模型和原SDK Python协议。原生硬件仍显式模拟，不打开真实相机/USB，不新增人体或Run测试，不改正式文件、电源、优先级、亲和性、GC或GIL切换间隔。

每窗最多12次计数读取：模型open前后、首个基类infer前后、第100/200个基类infer之后，以及GUI/模型/消费者在dense/mixed两个阶段点各一次。原函数的返回和异常保持；记录未包含CPU读取的原始方法墙钟边界，并与既有审计中的adapter ID、实际TID、ordinal及嵌套区间交叉核对。没有在所有推理或每帧消费上周期读取CPU，更没有原生计算预热。

每次保留原生GetProcessTimes/GetThreadTimes的user/kernel/creation、进程/线程cycles、PID/TID、CPython CPU时间包围核验及自身墙钟。调用线程不等于整个模型：原生worker计入进程CPU，未必计入这个Python调用线程。账本区间还包含并发GUI/消费者与观测开销，不能把processCPU全部归给模型。

Win64读取器使用局部ctypes.PyDLL，以保留每个短Win32只读调用的GIL，减少为观测而逐次释放/重新获取GIL的额外等待；不修改全局ctypes、原函数或系统设置，也不保证OS不会抢占。Native和完整capture边界仍各严格≤1ms，原合并context读数≤50ms；读取失败、超界、身份变化、计数倒退或实际工作期间计数不增长都不伪装成成功。这个读取方式也有扰动，不能据此关闭旧3%/1%或原生栈失败。

## 四窗预算与分析

全为original，没有候选、对照收益终点或全局设置干预。任何基础设施、完整数据/报告/状态、资源、context或CPU账本失败就停止后续窗口；超时保留PID和锁，先核对实际进程，不重启、不补采、不替换。无论是否出现快慢两态均在固定预算内停止。

precontact基类中位≥30ms暂标slow，≤26ms暂标fast，其间单列；边界源于既有队列，是探索性状态代理，不是CPU频率、根因、旧栈/扰动门槛或临床标准。至少20条完全在首个计划接触前的真实模型调用才描述该状态，保留所有调用和动态帧选择。若没有同时覆盖两种状态，就报告不能判别，不追加窗口凑状态。

`analyze.py`只读完成归档，分别给出open、首个基类调用、首调用至100/200次区间及三个角色dense→mixed的线程/进程CPU与cycles。实际CPU/等待/GIL持有者、硬件交付/内存/指令路径原因仍须额外证据；即使本账本全通过，也不自动得到正式修复资格。

归档器直接按plan中绑定的原stack_plan01路径/SHA检查458正式文件，避免此前归档器外部计划名替换错误；所有旧计划/失败、原CPU栈门槛保留。原始npz和完整归档只留本地/Windows忽略目录，同范围代码和派生结果继续推送现有分支。

执行器沿用既有cohort模板，头部旧A/A/AB说明不作为本次授权或预算；实际仅遍历plan01的startup01～04四个original案例，entry也明确拒绝其他backend。运行中的冻结源不为修正文案而修改。
