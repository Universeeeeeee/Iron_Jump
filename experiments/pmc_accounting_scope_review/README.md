# PMC 四窗口 CPU 记账范围复核

本阶段只复核 `c8ef572` 已保留的同一份四窗口 ETL；没有重跑窗口、修改原门槛或选择性放行七个通过阶段。空服务／交互激活候选只完成过准备，未启动，且不属于本 P0 结论。

## 83.612 ms 差异的可复核边界

`service01` 准备阶段的原始比较为：CSwitch 外包络 Running 5489.8624 ms，GetThreadTimes 5406.2500 ms，差 83.6124 ms。逐事件重新复核后：

- PID 17252、TID 7984 的 Thread Start v3 在准备标记前，Thread End v3 在消费标记后；四个原生标记的线程创建 FILETIME 完全相同，标记内部没有 TID 重用。
- 原生 `GetThreadTimes` 增量为 kernel 0、user 5406.25 ms；Python `thread_time_ns` 同为 5406.25 ms。两者同属 Windows 线程 CPU 记账体系，数值一致不能视为独立精度证明。
- 将每个 CSwitch 运行区间严格裁剪到两个原生 QPC 标记，Running 为 5489.8467 ms，残差仍为 **83.5967 ms**。原外包络边缘只增加 0.0157 ms，不能解释差异。
- 589 个运行区间跨 7 个逻辑 CPU，但区间并集与逐段求和完全一致，同时运行重复量为 0；迁移或重复累计不能解释差异。
- 2672019 行事件、2662348 个逐 CPU 相邻线程链、零报告事件／缓冲丢失及 10 MHz raw-QPC 时钟通过。独立两遍 ProcessTrace 的 54 个对应事件满足整数关系 `FILETIME_100ns − QPC = 常量`，残差为0。初次浮点复核曾显示16×100ns的跨度，那是FILETIME量级上的双精度ULP，不是实际时钟漂移；时钟转换不能解释83.6ms。

因此，已排除生命周期/TID重用、CSwitch边缘、跨CPU重复累计和QPC/FILETIME漂移。尚未解释的残差是 **83.5967 ms**。

## DPC／ISR 控制能说明什么

独立两秒空闲控制实际交付 DPC、TimerDPC 与 ISR-MSI；全部相关事件的原字节、CPU、字段和 InitialTime QPC 与 Windows `tracerpt` 独立解码及 API UTC/QPC 锚点吻合。它证实了后续方案能够记录这些区间。

该控制也证明系统端点累计量是粗记账：所有 CPU 的 DPC端点增量均为0时，ETW已有非零DPC区间；部分ISR端点按15.625 ms跳变。控制发生在之后的独立空闲窗口，不能回填旧ETL。

旧四窗口 ETL 没有 DPC／ISR 事件。ISR/DPC 在不发生线程切换时可以占用当前 CPU，因此是 CSwitch 驻留大于线程记账的合理候选；Windows统计记账粒度和其他内核记账范围也可能贡献。但现有证据不能把83.5967 ms分配给这些来源，更不能称为GIL等待。结论是：**中断时间尚不能解释该残差，缺失条件是同一实际负载窗口中的DPC／ISR区间。**

## 原 PMC 数据的可用范围

原31.25 ms门槛和 `service01` 准备阶段失败保持；两个阶段的原冻结跨状态比较全部继续扣留，不因另外七阶段通过而选择性放行。

仍可使用的证据包括输入/输出/模型结果身份、PID/TID生命周期、原生阶段边界、原始退休指令/Core/Reference/OS cycle计数和描述性信号。不能将其升级成原计划的合格效应估计或贡献比例。

另有一项独立硬件交付信号：八阶段中 `OS cycles / Reference` 均接近 CPUID leaf15 的 numerator/denominator = 200/2 = 100；慢窗 `Core / OS cycles` 约0.999，快窗约1.663–1.681。CPUID未提供晶振Hz，因此只保留无量纲比率，不换算GHz。该信号支持“慢窗的核心周期交付较低”，但不单独识别电源、温度、缓存、GIL或具体函数，也不解除原CPU记账门。

## 下一步

P0的旧证据复核已达到可说明的边界：83.5967 ms不能用现有ETL唯一解释，所缺的是同一负载中的DPC／ISR区间与更细的独立CPU记账。若必须重新观察，应采用一次有限、预先冻结的实际负载观察，同时记录DPC／ISR、CSwitch、PMC和原生边界；原四窗口的失败结论不得改变。
