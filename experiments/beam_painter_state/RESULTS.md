# 实验结果：像素等价通过，A/A 未通过，停止 A/B

本轮不建议移植到正式程序。候选优化的端到端性能收益尚未得到验证；没有运行 A/B、没有合并或移植。A/A 中走路恢复时间的配对中位差为 **+182.719 ms**，超过预先冻结的 ±150 ms 门槛。没有修改阈值或删除不利轮次。

基线 `e9be8a5`；分支 `codex/beam-painter-state`。实验于 2026-10-15 晚至 10-16 凌晨在 Windows LAPTOP-N03I4GMH（i5-9300H，8 逻辑处理器）运行。完整方法见 [README](README.md)，冻结条件见 [plan.json](plan.json) 及 [frozen_sources.json](frozen_sources.json)。

1. Mac / Windows 各 **1152/1152** 组 RGBA 字节完全相同；覆盖空场、连续活动、坏点、交替状态、768 束、DPR 1/1.25/1.5/2 等条件。见 [Windows 逐项像素结果](pixels_windows.json)、[Mac 逐项像素结果](pixels_mac.json)。
2. 两轮原绘图器功能检查通过；随后完成 **24 轮 A/A（每模式六对）**。每轮原始 bits/wire/validity/计数/顺序与源片段一致，stream/flags/drop 元数据一致；完整报告、质量历史、runtime/window、事件审计、timeline、mirror events 和原始归档与独立顺序 oracle 一致。只核对后归一化两处自检帧主机接收时钟。
3. 真实 SDK 启动、非零速度调用、实际骨架绘制、enabled GUI 和 SDK 关闭均有证据。图像来自固定原始 MJPEG，光束来自固定原始记录；没有实际 USB 光束采集和 DirectShow 相机采集负载。结果不能外推为真人现场持续 1000 Hz 验收。
4. Windows 任务正常结束（result=0），无遗留实验 Python / SDK 进程；已清理本轮计划任务。汇总取回时 SSH 曾断连，恢复后完整取回 24 轮记录，不补跑或替换轮次。
5. Mac 独立复核 24 轮，报告/原始数据/质量比较仍完全一致，验收判断一致；指标跨平台浮点复算最大差 2.14e-14，仅用于数值复算的容差不适用于像素和语义一致性。见 [复算检查](reanalysis_check.json)、[Windows 运行后审计](post_run_audit.json)。

## 恢复时间测量的额外问题

在未改变验收规则的事后检查中，用同一份 P 记录的完整批完成点重算原有恢复判据（连续 500 设备毫秒年龄 <=10 ms），发现共同稀疏点漏掉了短峰值：

- 走路第 3/4/5 对的 P：共同点分别为 1.010 / 0.180 / 0.114 s，完整批记录分别为 4.497 / 3.198 / 3.395 s。
- 跑步六轮 P：共同点均给出恢复时刻，完整批记录均未在剩余片段中满足持续门槛，保留为 null。
- 后接触阶段 P 批记录的年龄中位数：走路约 1.73–1.89 ms，跑步约 2.13–2.20 ms；仍出现约 81–108 ms 的短峰值。因此“没有连续 500 ms 全部低于 10 ms”不能等同“队列从未排空”。本轮没有记录实际队列深度。

这直接表明该持续门槛对观察分辨率和短时抖动敏感。不能把走路 +182.719 ms 解释为 P 自身增加了同等计算成本，也不能仅凭跑步中位差通过宣称恢复测量可靠。详细原数见 [recovery_resolution_sensitivity.json](recovery_resolution_sensitivity.json)。这是补充诊断，不替换失败的 A/A，不启用 A/B。

尚未区分的因素：P 观察器增量开销、GUI/SDK/推理与 Windows 调度的短时波动、源线程迟到、稀疏采样遗漏峰值。调度器每约 3 秒查询任务状态的共同背景负载也属于实验条件，未被 L/P 增量校准单独排除。
