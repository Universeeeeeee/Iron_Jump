固定原图均为1080×1920×3。源码 `vision/live_walking.py` 的 `_PreviewAdapter.infer_bgr` 在宽度大于640时调用 `cv2.resize`，因此这是直接可检查的候选路径；未用完整调用栈证明该算子就是这些线程的创建者，更不能称其为积压根因。

## 本轮保留的失败

3个新增线程的运行时系统查询均返回 `0xC0000022`（STATUS_ACCESS_DENIED）。查询通过0x0800有限信息权限打开句柄，未能完成类9入口查询；这些失败与已关闭句柄均记录在 `accounting01.json`。本轮入口模块结论来自已校准ETW字段和ImageLoad映射，**没有本窗口的系统查询双重核对**。

这项工具问题不阻止读取本轮生命周期及选择下一对照，现阶段不再为它扩展合成工具，也不重跑本窗口补成功。未来若需要该接口，必须另行修正、验证并冻结版本。

## 支持、削弱与唯一后续干预

**支持的方向：** 模型原生流水线与消费者并发时存在值得验证的资源竞争/执行成本问题。它包含OpenCV路径，不能提前把全部责任归给MediaPipe。新线程是工作期内的活动，不是只在退出清理时出现。

**被削弱的解释：** 只等ready就能解决；只修一个array_equal边界就能稳定解决；这轮的全部消费者延迟都来自等待；初始线程创建本身足以解释所有后续慢调用。这些判断均不等于排除其他窗口中的GIL或系统等待。

**只选择一项后续干预：固定原工作“并发释放”与“消费者完成后再释放模型工作”对照。** 两臂均保留原函数、同一模型线程、全部输入和完整返回身份，只改变实验工作重叠。它用于回答模型流水线并发是否导致消费者显著变慢，不把串行调度当作正式架构修复。

预算和方向性判据已写入 `next_decision01.json`：4对、固定平衡顺序、不补样本；全部语义相同，4对均改善且几何平均消费墙钟降幅至少20%，才优先推进该机制。原3%/1%失败不更改，这不是小收益或GIL份额证明。该对照尚未执行。
