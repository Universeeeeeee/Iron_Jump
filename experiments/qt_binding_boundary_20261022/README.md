# Qt 运行时不一致与两处高频调用边界

生产基线仍为 `10014b5c`，本目录只增加离线实验及证据。未打开设备、相机、USB或SDK，未启动人体/Run测试，未修改正式代码、默认后端、坏束登记、NumPy、滤波、Processor或绘图。

## 新发现与原结论修正

`b4a008a4` 的真实GUI验证入口 `live_consumer_process_candidate/gui_launch17.ps1` 明确设置 `QT_API=pyqt5`；当前正式桌面入口明确设置 `QT_API=pyside6`，后者原文及SHA见 `evidence/environment_audit.json`。历史GUI报告未保存目标进程完整Qt库身份，所以不能把现在的库版本倒填为历史实测值。

上一轮 `wire_boundary_replay_20261022/matrix02` 日志四窗均出现PyQt5字体路径，直接读取当前SSH环境也选择PyQt5。其“子进程无明显增长”不能直接外推到要求PySide6的正式入口。另一个更早的 `measurement_boundary_replay_20261022/matrix02` 未保存实际绑定，不能从无字体警告反推绑定。原源码哈希相同不足以证明运行时相同。

新窗口在每个父/子进程核对实际QObject/QApplication来源、Qt版本、QtCore二进制SHA和已加载绑定集合；只接受期望绑定且拒绝混装。实际为PyQt5/Qt5.15.2或PySide6/Qt6.11.1。16窗全部正常完成，生产文件哈希不变；均为Session0、Normal(32)、offscreen。此上下文仍不是交互桌面。第一次临时上下文查询的priority=0没有完整ctypes原型，不采用；新窗口使用显式原型并拒绝零返回。

## 信号路径校正后的同输入结果

所有窗口使用 `20261022_085545_9550a923` 的同一留存帧、原完整处理链和真实ExecutionView控件。逐段协议包及2048字节读取/20ms批次节奏为合成控制，原USB到达模式未知。

PySide6本地窗口已出现秒级消费侧积压，子进程仍有残余增长；消费后发送/接收/分发/绘制不是这组秒级增长的主要位置。它支持进一步检查Qt/Python交接，尚不能证明现场三秒全部由运行时迁移造成，更不能称PySide6普遍较慢。

## 分开干预两处高频边界

两组都只用PySide6、process40和校正后的单信号输入。固定qt/python/python/qt四窗；每组只改变一处调用，其他Qt信号保留。线程、参数身份、入队顺序和完整报告分别核验。直接回调仅是诊断候选，尚未验证生产异常、断连和全部生命周期语义。

1. `matrix03`：`DeviceQualitySession.frame_ready → GaitEngine.process_quality_frame`。两端同一测量线程；换成该线程直接调用。Qt两窗增长761.434/775.365ms，直接调用两窗559.099/463.647ms。**第三窗与一次单元验证进程重叠，排除出干净因果比较**，只保留描述结果；第一对为761.434→559.099ms。完整原窗、测试日志及文件时间界限均保留，没有补跑替换。
2. `matrix04`：恢复原质量Qt信号，只改变 `sensor_frame_received → _GroundFrameInbox.on_frame`。原DirectConnection已经在读取线程执行入队，不需要切换到测量线程；候选直接调用同一个锁保护入队方法。Qt两窗增长387.516/536.203ms，直接调用两窗200.213/307.071ms。各窗实际读取线程身份、投递帧数及报告一致。

两处干预的方向均支持“高频Qt/Python交接是可干预的积压放大点”，但单独绕过任一处均未消除积压，不能定为唯一根因。不同矩阵不能相减计算各边界贡献，也不将直接调用收益全部命名为GIL等待。Qt版本、绑定实现和事件调度差异仍未拆开。
