## 冻结方法

`plan.json`、`frozen_sources.json` 在正式重复前冻结。`harness_versions/smoke01/` 保留功能检查使用的先前脚本与计划，`smoke01_validation.json` 仅是 5 秒功能检查，不计入正式结论。功能截图保留在忽略的 `runs/smoke_01_walk/`。

- 一个正式默认 `UsbWorker → _GroundFrameInbox → DeviceQualitySession → GaitEngine`；没有旁接逐帧信号、额外实时帧列表、回放构造或第二路输入。停止后保存原有 `OvergroundSession` 的接触位与设备时间戳，不新增线缆原始包采集。
- 真实 Windows enabled `ExecutionView`、正式相机预览与正式 `GroundChannelWidget.paintEvent`。除计数包装外，调用原渲染函数。SDK 既有遥测仅做计数。
- 沿用上一轮逐字节相同的 QueueProbe P：64 样本桶的批次完成快照与 10 Hz 待处理队列快照。没有新增高频 Python 调用树、ETW 或 CPU 采样。该探针并非零扰动，不能用本轮结果证明无探针程序的表现。
- 走路、跑步模式交错，共 6 个独立 Python 进程，每进程先冷启动 30 秒、再预热 30 秒，各模式各 3 对，共 12 阶段。冷启动指进程首次正式采集，已通过原有预检和首次真实预览/SDK 启动；不代表操作系统重启、相机断电或文件缓存清空。预热阶段保留同进程相机/SDK/推理，间隔 3 秒，正式控制器重新准备 USB 与引擎。
- 首个正式 11 秒为主窗口，之后至 30 秒为次窗口；首次 USB 接收起的 11 秒另列，包含预检/启动，不能与相机已就绪正式窗口混淆。正式停止后的排空不计入吞吐窗口。

持续消费不足门槛（正式前声明）：窗口入队进度至少 990 fps、消费进度低于 970 fps、真实待处理至少 100 帧且最老帧至少 100 ms，连续观测跨度至少 1 秒、相邻重积压观测间隔不超过 250 ms，并且完成帧接收年龄的增长斜率超过 10 ms/设备秒。任一有效正式主/次窗口满足，才进入独立原生调度记录校准。`reproduction_gate.rule` 是触发条件；`native_stage` 中“initial”是较窄的文字描述，初始/后续窗口分别报告。

队列深度是锁内实际 deque 长度，最老年龄来自实际队首的 `received_monotonic_ns`。批次尚未确认完成的样本数包含批内已处理部分，不能当作逐帧精确在途计数。入队进度来自质量会话最近接收帧，时间戳在 USB 读取/组帧后生成；其“约 1000 fps”不能单独证明设备在原生 USB 层均匀交付。若采样线程被整体饿死，观测空洞必须保留，不能填充成持续积压。
