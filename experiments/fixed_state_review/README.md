## 同窗三个阶段

检查共同原始 `fixed_overlap_comparison/workload.py`：模型 `open()` 完成并发出 ready 后，模型线程等待 `go`；消费者先重放前 42,237 个历史帧，随后才开始被计量的 6,824 帧。并发模式此时才释放 220 次推理，串行模式在消费结束后释放。因此 `ready_ns → consumer.begin_ns` 提供一个**正式模型推理尚未开始时的准备阶段墙钟代理**。它包含协调线程唤醒、时钟设置及进程计数开销，没有独立准备 CPU 边界；不能伪装为纯循环 CPU 时间。模型原生空闲线程仍存在。

## 判断变化

1. 慢状态并不只出现于接触负载与模型推理同时运行期间：同窗准备阶段已经较慢，消费结束后模型尾部仍慢。纯粹的“双方当前同时运行导致全部慢态”解释不足。
2. 消费 CPU 与墙钟一起明显变化，特别是串行窗口；这进一步削弱“新增阻塞等待单独解释全部秒级差异”。线程 CPU 时间不等于指令数，CPU 交付速度、缓存/内存、实际执行路径、原生线程后台活动仍不能区分。
3. 历史 25.4% 的并发方向性证据继续保留；本次没有推翻并发贡献，也没有把剩余成本分配给 GIL、GUI、模型或设备。
4. 所有窗口模型关闭都约 42.05–42.12 秒，关闭在工作计数之后，不能计入消费成本。它影响整个队列试次间隔，不能假定这是紧接运行的热态基准。

**现在优先缺的是同窗实际 CPU 交付/系统运行状态证据，而不是另一项局部函数优化。** 当前 i5-9300H 是 4 核 8 逻辑处理器；事后读取的活动电源方案为平衡，电池状态 2、98%。Win32_Processor 两个时钟属性均为 2400MHz，不能据此认定当时有效频率为 2.4GHz。进程 cycles / CPU time 也不能充当实际频率计；没有温度、节流原因、有效频率、历史电源来源或外部负载证据。没有改变电源方案。
