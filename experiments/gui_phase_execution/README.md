# 同模型线程初始化前后执行能力观察：准备阶段

现有GUI严重首窗在接触前已慢，但此前原生探针在应用初始化前约9秒，未覆盖后续阶段。本方案只回答一个问题：同一真实GUI进程的同一模型线程，在原模型open前后，固定原生计算的实际速度是否发生大变化。不是再一次QoS优化A/B，也不替换旧失败窗口。

复用 `cpu_execution_probe/probe.py` 和其原计划，字节码、六段固定工作量、正控制、输出和内存释放检查不变。仅在 `MediaPipePoseAdapter.open` 前后及 `close` 后各执行一次，保留独占目录。分别记录内部原open/close的实际边界；外层既有审计会包含探针时间，分析必须明确区分两者。

预计探针每阶段约0.8秒，会改变初始化/ready及清理时序，不能宣称无扰动，也不能将本批GUI延迟作为性能修复验收。不会在消费或推理循环中插入周期采样，不修改正式文件或原算法。

`preparation01.json` 固定两窗，默认QoS、同一交互优先级、原GUI和保存Walk/模拟SDK。必须核对三个阶段都属于同一模型TID、原生输出精确且四倍量比例通过、完整原工作语义与最终清理通过。两窗均同向至少15%的after-open/before-open吞吐变化，才支持与初始化关联的执行状态变化；无变化或未覆盖两种状态不追加窗口，不换成已知快窗比较。无论结果如何，都不直接解释为GHz、温度、GIL份额或唯一根因。

本地6项测试通过；Windows同一组测试结果保存在 `windows_tests01.json`。测试覆盖原返回值、原异常、probe顺序、失败后不造后置结果、重复open/close拒绝，以及基类包装和既有外层审计的继承调用链。没有运行真实原生探针、GUI或模型。
