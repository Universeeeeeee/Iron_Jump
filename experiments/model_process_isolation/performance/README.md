## 交付完整，机制仍有限

8窗全部完整原始语义、报告及220个模型返回身份与同一参考完全一致；4个隔离窗都验证了真正不同PID、图像哈希、实际推理区间在父RPC区间内且与消费重叠、模型关闭和父子退出。没有通过减少模型工作、删帧或不同结果换得改善。

父进程CPU在隔离组大幅减少主要因为模型迁出，不能称为总CPU节省。父模型线程成为IPC代理；真实模型子进程CPU分别10015.625、10046.875、9562.500、9359.375ms，单独保留，不和父边界不同的计数相减为GIL或等待份额。

整组墙钟指既有工作计数边界覆盖的消费者与模型工作；模型open、准备图像传输和close不在这个终点中。它不是进程从启动到退出的总时长，后续架构决策必须另外考虑启动及IPC成本。四对相同计数边界没有因此被静默更改。

**停止将“仅把模型放到子进程”作为当前修复路线。** 这不证明整个进程隔离思路无效：本任务无GUI，未隔离消费与绘制的共享进程条件；系统CPU/缓存资源也仍共享。不能把此4.8%与另一批串行25.4%相减得到GIL/缓存责任，也不能由当前差异推断此前GUI严重状态的主因。

下一步先审查原消费者与GUI共享执行边界及可保持完整语义的隔离单位，而不是重做本候选或直接修改正式线程结构。原GUI1000Hz pending/contact→paint症状、稳定基线复现与正式修复仍未验证；当前不需要增加真人测试。
