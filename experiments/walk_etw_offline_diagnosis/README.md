# Walk 四轮：现有数据离线调度诊断

日期：2026-10-17。分支：`codex/walk-etw-offline-diagnosis`；从 `dd14a78` 建立，仅新增离线读取、分析、测试与证据。没有启动现场采集、相机、SDK、USB、WPR 会话或性能优化 A/B，没有修改正式代码、冻结实验运行源、NumPy 或绘图候选。

## 结论与证据边界

已证实的机制层事实：光束已经进入队列，但消费者服务率在部分接触阶段低于输入，导致脚印事件在到达 GUI 前累积数秒延迟。第 2 轮 ON 与第 4 轮 OFF 均有该事实，因此 ETW 不是出现异常的必要条件。第 2、3 轮的差别不能用“consumer 一次停了几秒”“Ready 队列长时间不调度”解释；也不能仅由实际骨架绘制次数解释。

现有证据足以提出可证伪的根因假设，尚不足以确认某个函数、GIL、GC 或 Qt 路径是根因。特别是 CSwitch 驻留时间与独立 CPU 账本存在明显差异，不能将 Running 当作独占计算成本，也不能把 ON 的调度模式套到 OFF。

## 解码、线程身份及时间校验

- Windows 原生 `OpenTraceW / ProcessTrace` 只读取已保存 ETL；分别使用 `PROCESS_TRACE_MODE_EVENT_RECORD=0x10000000`，以及加 `RAW_TIMESTAMP=0x1000` 的两次消费。没有开启跟踪会话。
- CSwitch v5 载荷 28 字节：读取 Microsoft TraceEvent 对 >=v2 定义的稳定前缀：新/旧 TID 位于 0/4，旧等待原因/状态位于 12/14。未知尾部 4 字节不解释；完整 ETL 保留。ReadyThread v2 为 8 字节，目标 TID 位于 0。不能因 XML 未解释二进制而认定事件不可用。
- 同 CPU 相邻 CSwitch 的上一 NewThreadID 必须等于下一 OldThreadID；逐线程 in/out 必须交替且运行区间内不发生无记录迁移。正式窗口状态覆盖完整，未将缺失 ReadyThread 强制计为 Waiting；状态为 Running 的切出记录保守留为 Transition。
- 以生命周期 DCStart/End 核对原生线程 ID 属于本轮 GUI 进程，没有 TID 复用污染。所有时间比较使用原始 QPC、保存的 perf/FILETIME 括号，不使用 XML 的 +07:59 字符串或粗糙 BootTime。

|---|---:|---:|---:|---:|---:|---|
|2 ON|1,543,091|871,912|242|29.75 µs|13992|18100 / 20580 / 20688|

两轮原始/Windows UTC 转换的偏移在各自整轮内完全恒定；全部逐 CPU 切换链零断裂。事件计数与独立 tracerpt 全扫描完全一致，原 ETL SHA256 与先前记录一致；文件头与全扫描均无丢失事件/缓冲区。ReadyThread 的 header TID/PID 在这些经典事件中为无效值，不能据此识别唤醒者或锁持有者。

比较窗口严格使用保存的两组 CPU 读取时间括号；逐线程核对身份，并给出括号引起的 Running 上下界。不能把正式 arm/stop 的几毫秒偏差当作 CPU 账本差异的解释。

Running 是两次切换之间的调度驻留墙钟时间，不等同线程实际被计费的执行 CPU；ISR/DPC、调度开销、CPU 账本粒度/实现及虚拟化等均可能造成差异，当前不能选定其中某项。采集 profile 没有请求 ISR/DPC 区间、CPU 采样或调用栈，现有数据不能完整拆分此差额。本报告不缩放曲线凑齐 CPU 时间，不将驻留/样本代理量称作 NumPy、滤波或 Processor 独占耗时。

## 第 2、3 轮线程状态与长停顿

下表为各轮冻结定义的输入密集窗：第 2 轮设备秒 9–14，第 3 轮 9–13；它们不是相同输入。Ready 包含已具备调度资格的 Standby/DeferredReady，保守 Transition 占比不足 0.003%，未隐藏为 Waiting。该表描述调度事件含义，不解除上述执行 CPU 归因限制。

|轮次|线程|Running 驻留|Ready|Waiting|全程最长未运行间隔|
|---|---|---:|---:|---:|---:|
|2|consumer|41.58%|7.73%|50.69%|6.530 ms|
|2|gui|53.39%|4.07%|42.54%|32.818 ms|
|2|reader|23.83%|8.47%|67.70%|6.487 ms|
|3|consumer|44.75%|8.07%|47.18%|6.114 ms|
|3|gui|55.00%|3.65%|41.35%|39.785 ms|
|3|reader|15.71%|9.21%|75.08%|6.110 ms|

consumer 密集窗最长 Ready 区间分别为 0.684、0.611 ms；全程最长未运行间隔分别为 6.530、6.114 ms。没有一次数秒的 consumer 停止调度，也没有数秒的 GUI 停止调度；**这不能排除 GUI 长回调或事件排队，也不能排除 GIL**，因为等待 GIL 可表现为 Waiting，而非 Ready。

绝大多数 consumer Waiting 的原始等待原因值为 6，不能识别是 GIL、Qt/系统同步、互斥锁或某个 Python 调用。低频队列探针与原生状态关联后，在远离状态边界 >0.1 ms 的少数点能看到 pending>100、batch 在途同时 consumer Waiting（第 2 轮 1 点，第 3 轮 3 点）；说明这些点仍位于 `_consume` 内，不能一概解释为等待下一次 drain。但 Python 探针本身也可能竞争 GIL，这不是无偏等待占比或锁持有者证据。

## 脚印延迟分解：界限而非嵌套耗时相加

原始 `published_sample` 是设备样本号，不是主机发布时间。利用同一 consumer 在线程内、批次完成后记录的 queue_common 点，对实际发布主机时间给出上下界；独立观察线程的 queue_samples 不用于构造这个下界，因为发布可能早于该批次全部完成。再与 GUI 首次收到 confirmed 脚印及首次 paint 对齐。下表取各轮最后一个已发布脚印。

|轮次|发布样本收件→算法发布界限|算法发布→GUI 收到的上界|GUI 收到→首次绘制|触地样本收件→首次绘制|
|---|---:|---:|---:|---:|
|1|3.3–115.8 ms|11.0 ms|29.9 ms|88.2 ms|
|2|4929.5–5042.0 ms|88.3 ms|36.1 ms|5105.3 ms|
|3|505.0–572.6 ms|29.5 ms|33.2 ms|612.3 ms|
|4|5466.5–5728.6 ms|91.9 ms|75.3 ms|5677.4 ms|

第 2 轮最后脚印到 GUI 前已有约 4.93–5.04 秒等待，第 4 轮 OFF 为 5.47–5.73 秒；分别在 GUI 收到后约 36/75 ms 首次绘制。四轮所有已发布脚印的 GUI 投递上界均不超过约 173 ms，GUI 收到到绘制最大约 128 ms。故这两轮的多秒级已发布脚印延迟主要在 GUI 收到事件之前。算法确认所需设备样本间隔、消费积压、GUI 投递和 paint 不是彼此可重叠相加的函数独占耗时。本分析仅给区间，不把原始脚步发布缺失纳入延迟统计，也不声称等同真实屏幕曝光延迟。

## 按证据排序的解释与剩余假设

1. **已证实：部分接触状态下的消费者服务率不足是排队发生的位置。** 对应样本已到达，队列保存且最终排空；ON2 的多秒脚印等待发生在 GUI 收到前。OFF4 独立证明同样的机制层异常不需要 ETW 开启，不能借用 ON2 的状态比例解释 OFF4。
2. **优先验证：接触处理路径的单位样本进展变慢，可能来自执行需求、同步开销或驻留内有效 CPU 交付变化。** ON2/ON3 的 consumer Running 份额差别约 3.2 个百分点，消费速率却接近差一倍；以批次计数粗算的驻留/完成帧代理量约 0.867/0.469 ms。这个量包含非执行 CPU 时间和边界误差，不能当作算法独占成本。已消费接触负载与吞吐变化相关，值得优先核验质量处理、稳定滤波、WalkingProcessor 各自的执行及等待来源，但不能选择其中一个当成已证实热点。CPU 频率、存储层次或中断等未测因素也不能凭这些数据排除。
3. **可能但未证明：GIL 或其他锁/同步竞争。** Waiting 多、存在批次在途等待、短间隔高频切换均与此相容；等待原因、无效唤醒者字段及缺少栈/持有者信息，使它无法与 Qt/系统同步或原生库等待分开。不能把 Waiting 一律标成 GIL，也不能由调度现象推断 GC。
4. **不支持作为主要单一解释：一次数秒 Ready 停顿、GUI 未获调度数秒、单纯上游晚到或骨架次数多少。** 但短时输入交付波动、Qt 事件投递/回调忙碌、每次渲染或推理成本变化仍可能贡献；未测得的独占阶段成本和 ISR/DPC/CPU 计费差额仍是限制。

## 现有证据是否足以确认可修复根因？

**还不足以确认具体根因或提出已验证的最小性能修改；足以提出上述可证伪假设并排定验证顺序。** CPU 交叉校验已经完整执行并披露差异，没有因为数据互相吻合便把驻留时间包装成算法 CPU。现有 ETL 缺少的调用栈、等待对象及 ISR/DPC 区间不能靠离线补算生成，本轮分析到此有明确证据上限。后续若要继续，应先设计经独立校准的最小原生栈/等待来源与 CPU 记账验证，区分“执行需求增加”与“批次内等待”；不能直接调整 drain/回放等待策略、增加高频 Python 调用树或进行性能重构。此处仅提出验证方法，本轮不采集。

## Run 能提供什么新的判别证据？

普通地重复 Run OFF/ON/ON/OFF，主要增加“是否跨模式复现”的证据，不能自动分辨 GIL、Qt 或每阶段计算成本。Run 同时改变 Processor、接触持续时间/几何、通过速度、SDK 运动和骨架负载；更快或更慢都不是单独针对某个根因的检验。同样的无栈 ETW profile 也补不上当前缺失的等待对象和 CPU 记账来源。

因此目前**不建议为了定位立即增加现场 Run**。只有事先规定可区分假设的条件，且检查输入密度、实际骨架/SDK 与 CPU 账本可比性后，跨 Walking/Running 的差异才可能收敛到共享链路还是模式相关路径；仍需单独定位，不能由“Run 正常”排除共享链路或由“Run 也慢”确认 GIL。已有 Run 正确性、步数与脚印问题继续独立处理。
